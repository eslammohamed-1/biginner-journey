<small>المرحلة 5 · npm بالتفصيل</small>

سارة عملت clone لمشروع زميلها، وكتبت npm install، والمشروع ضرب Error مش موجود عنده. نفس الكود، نفس package.json. الفرق؟ نسخ مختلفة جوه node\_modules. الفصل ده بيحل اللغز: نظام أرقام النسخ (SemVer)، ومعنى كل رمز (^ و ~ و x و \>=)، والـ Lockfile اللي بيقفل كل نسخة، والفرق بين npm install و npm ci و npm update، و npm outdated بيقرا إيه.

:::note[بعد الفصل ده هتكون عارف]
- تقرا أي رقم نسخة: MAJOR.MINOR.PATCH ومعنى كل جزء
- تعرف كل Range يقبل إيه: ^ و ~ و x و \* و \>=
- الاستثناء بتاع 0.x والـ Prerelease
- dist-tags: latest و next و beta
- package-lock.json: بيسجل إيه، وليه يترفع على Git
- npm install ولا npm ci ولا npm update
- تقرا جدول npm outdated (Current و Wanted و Latest)
:::

<a id="s15-1"></a>

## 15.1 اللغز

في `package.json` مكتوب `"vite": "^8.3.4"`. يعني إيه بالظبط؟ "Vite 8.3.4"؟ لأ. القالب كاتب كده، والمتسطب عندنا طلع **8.3.5**. فلو زميلك سطّب الشهر اللي فات، أخد 8.3.4، وانت النهارده أخدت 8.3.5. ولو 8.3.5 فيها Bug… "بيشتغل عندي". علشان تفهم ده، محتاج تقرا الرقم الأول.

<a id="s15-2"></a>

## 15.2 SemVer: تلات أرقام وكل واحد ليه معنى

![8.3.5 = Semantic Versioning: الرقم نفسه بيقولك التحديث آمن ولا لأ.](./assets/ch15-fig1.png)

*8.3.5 = Semantic Versioning: الرقم نفسه بيقولك التحديث آمن ولا لأ.*

دي **وعد** من صاحب المكتبة: "لو غيرت حاجة تكسر الكود بتاعك، هزوّد الـ MAJOR". فمن Vite 7 لـ Vite 8 (Rolldown بدل esbuild و Rollup، فصل 18) ممكن تحتاج تعدّل حاجات. لكن من 8.3.4 لـ 8.3.5؟ المفروض صفر تعديل. و`semver` (الـ Package اللي npm نفسه بيستخدمه) بيحسبها:

```sh title="Terminal"
$ npx semver -i patch 1.2.3
1.2.4
$ npx semver -i minor 1.2.3
1.3.0
$ npx semver -i major 1.2.3
2.0.0
```

لاحظ: لما الـ MINOR يزيد، الـ PATCH يرجع صفر. ولما الـ MAJOR يزيد، الاتنين يرجعوا صفر.

<a id="s15-3"></a>

## 15.3 الـ Ranges: كل رمز يقبل إيه

بدل ما نحكي، اديناله نفس قايمة النسخ (`1.2.2 1.2.3 1.2.9 1.3.0 1.9.0 2.0.0` ومعاهم `1.3.0-beta.1` و`1.2.4-rc.1`) وسألناه كل Range بيقبل إيه:

```sh title="Terminal"
$ npx semver -r "^1.2.3" 1.2.2 1.2.3 1.2.9 1.3.0 1.9.0 2.0.0 1.3.0-beta.1 1.2.4-rc.1
1.2.3
1.2.9
1.3.0
1.9.0
```

**النتايج الحقيقية لكل Range على نفس القايمة**

| الـ Range | قبل | بالعربي |
|---|---|---|
| `^1.2.3` | 1.2.3 · 1.2.9 · 1.3.0 · 1.9.0 | أي حاجة من 1.2.3 لحد قبل 2.0.0. **الافتراضي** لما تعمل `npm i`. |
| `~1.2.3` | 1.2.3 · 1.2.9 | Patches بس: لحد قبل 1.3.0. |
| `1.2.3` | 1.2.3 | بالظبط (اللي بيعمله `-E`). |
| `>=1.2.3 <1.3.0` | 1.2.3 · 1.2.9 | نفس `~1.2.3` مكتوبة صريح. |
| `1.x` | 1.2.2 · 1.2.3 · 1.2.9 · 1.3.0 · 1.9.0 | أي 1 (حتى الأقدم من 1.2.3). |
| `*` | كل اللي فوق + 2.0.0 | أي حاجة. خطر. |

ولاحظ إن **ولا Range** قبل `1.3.0-beta.1` أو `1.2.4-rc.1`. دي **Prerelease** (نسخ تجريبية بشَرطة بعد الرقم)، و npm مش بيديهالك إلا لو طلبتها صريح: Range زي `^1.2.4-rc.0` قبل `1.2.4-rc.1` (نفس 1.2.4) بس رفض `1.3.0-beta.1`.

### الاستثناء: لما الـ MAJOR يبقى صفر

```sh title="Terminal"
$ npx semver -r "^0.2.3" 0.2.2 0.2.3 0.2.9 0.3.0 1.0.0
0.2.3
0.2.9
$ npx semver -r "^0.0.3" 0.0.3 0.0.4 0.1.0
0.0.3
```

نسخ `0.x` معناها "لسه بنجرّب، أي حاجة ممكن تتكسر". فالـ `^` بتبقى أحرص: `^0.2.3` بتتصرف زي `~`، و`^0.0.3` بتبقى نسخة واحدة بس. القاعدة: `^` مابتغيرش أول رقم مش صفر.

:::note[من الـ Terminal بتاعك]
عايز تعرف Range معين هيجيب إيه دلوقتي؟ `npm view react@^18 version` بيعرض كل النسخ المطابقة. جرّبناه، وآخر سطور كانت `react@18.3.0 '18.3.0'` و`react@18.3.1 '18.3.1'`. و`npm view vite@~8.2 version` رجّع 8.2.0 و 8.2.1 و 8.2.2 و 8.2.4 (مفيش 8.2.3 منشورة). يعني لو حد كتب `~8.2` هياخد 8.2.4.
:::

## 15.4 dist-tags: latest مش دايماً الأحدث رقماً

```sh title="Terminal"
$ npm view vite dist-tags
{
  alpha: '6.0.0-alpha.24',
  beta: '8.3.0-beta.1',
  latest: '8.3.5',
  previous: '6.4.5'
}
$ npm view react dist-tags
{
  …
  next: '19.3.0-canary-d5736f09-20260507',
  latest: '19.3.1',
  backport: '19.1.10',
  …
}
```

الـ **dist-tag** اسم بيشاور على نسخة. `npm i vite` = `npm i vite@latest`، و`latest` هي اللي صاحب المكتبة شايفها مستقرة. و`npm i react@next` بيجيب النسخة التجريبية. فـ `npm create vite@latest` معناها "النسخة اللي عليها tag اسمه latest".

## 15.5 الـ Lockfile: الحل

الـ Range في `package.json` بيقول "أقبل إيه". لكن `package-lock.json` بيسجل "**اخترت** إيه بالظبط"، لكل Package في الشجرة (مش اللي انت طلبته بس):

```dockerfile
{
  "name": "np13",
  "version": "1.0.0",
  "lockfileVersion": 3,
  "requires": true,
  "packages": {
    "": {
      "name": "np13",
      "dependencies": {
        "lodash": "^4.17.20", …
    "node_modules/lodash": {
      "version": "4.17.20",
      "resolved": "https://registry.npmjs.org/
        lodash/-/lodash-4.17.20.tgz",
      "integrity": "sha512-PlhdFcillO…",
      "license": "MIT"
    }
```

1. `{`: نسخة صيغة الملف. 3 = صيغة npm 7 وأحدث.
2. `"packages": {`: `""` = مشروعك نفسه، ومعاه نسخة من الـ Ranges.
3. `"node_modules/lodash": {`: النسخة اللي **اتسطبت فعلاً**.
4. `"resolved": "https://registry.npmjs.org/`: نزلت منين بالظبط.
5. `"integrity": "sha512-PlhdFcillO…",`: بصمة الملف (Hash). لو حد غيّر الملف على السيرفر، البصمة مش هتطابق والتسطيب هيفشل. ده حماية (فصل 16).
6. `"license": "MIT"`: والـ License كمان.

:::tip[القواعد الثلاثة]
- **ارفعه على Git دايماً** (مع `package.json`). و`node_modules` لأ (`.gitignore`، كتاب Git فصل 5).
- <strong>متعدّلوش بإيدك.</strong> npm هو اللي بيكتبه.
- <strong>متمسحوش علشان تحل مشكلة.</strong> مسحه = كل النسخ ممكن تتغير مرة واحدة. ولو حصل Conflict فيه في Git: خد نسخة أي فرع، وشغّل `npm install`، وهو يظبط نفسه.
:::

## 15.6 install ولا ci ولا update؟

جرّبنا التلاتة على مشروع فيه `"lodash": "^4.17.20"` والـ Lockfile مسجّل 4.17.20، والأحدث المتاح 4.18.1:

```sh title="Terminal"
$ rm -rf node_modules && npm ci
$ npm ls lodash
np13@1.0.0 /tmp/np13
└── lodash@4.17.20
$ npm update
changed 1 package, and audited 4 packages in 366ms
found 0 vulnerabilities
$ npm ls lodash
np13@1.0.0 /tmp/np13
└── lodash@4.18.1
$ npm pkg get dependencies.lodash
"^4.17.20"
```

**التلات أوامر**

|   | `npm install` | `npm ci` | `npm update` |
|---|---|---|---|
| بيقرا | package.json + Lockfile | الـ Lockfile بس | package.json |
| النسخ | اللي في الـ Lockfile لو لسه بتطابق | الـ Lockfile بالحرف | أحدث نسخة جوه الـ Range |
| بيغيّر الـ Lockfile؟ | لو لزم | أبداً | أيوه |
| node\_modules | يكمّل على الموجود | يمسحه ويبدأ من الصفر | يحدّث |
| إمتى | بعد clone، أو لما تزوّد Package | في الـ CI والـ Deploy (فصل 25) | لما تقرر تحدّث |

لاحظ إن `npm update` غيّر لـ 4.18.1 (جوه `^4`) بس **ماغيرش** `package.json`: لسه `^4.17.20`، والـ Lockfile هو اللي اتغير لـ 4.18.1. و`npm ci` صارم، وده المطلوب في سيرفر الـ Deploy:

```sh title="npm ci من غير Lockfile"
x npm error code EUSAGE
x npm error The `npm ci` command can only install with an existing package-lock.json or
x npm error npm-shrinkwrap.json with lockfileVersion >= 1. Run an install with npm@5 or
x npm error later to generate a package-lock.json file, then try again.
```

```sh title="npm ci بعد ما غيرنا package.json لـ ms@^1.0.0 من غير install"
x npm error `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync. Please update your lock file with `npm install` before continuing.
x npm error Invalid: lock file's ms@2.1.3 does not satisfy ms@1.0.0
```

التاني ده بالظبط اللي هيحصل لو عدّلت `package.json` بإيدك ونسيت تعمل `npm install` قبل الـ commit: الـ Deploy هيفشل (فصل 25).

## 15.7 npm outdated: مين محتاج تحديث

```sh title="Terminal"
$ npm outdated
Package  Current  Wanted  Latest  Location             Depended by
lodash   4.17.20  4.18.1  4.18.1  node_modules/lodash  np13
ms         2.0.0   2.0.0   2.1.3  node_modules/ms      np13
```

| الأمر | بيعمل إيه |
|---|---|
| `Current` | المتسطب دلوقتي. |
| `Wanted` | أحدث نسخة الـ Range بتاعك يسمح بيها. ده اللي `npm update` هيجيبه. شوف `ms`: الـ Range `~2.0.0`، فالـ Wanted لسه 2.0.0 مع إن فيه 2.1.3. |
| `Latest` | الـ `latest` tag. علشان توصله لو برة الـ Range: `npm i ms@latest` (وده بيغيّر الـ Range في package.json). |
| `exit 1` | الأمر بيرجع exit code 1 لو فيه حاجة قديمة. مش Error، دي علشان الـ Scripts تعرف. |

:::note[التحديث على MAJOR جديد]
لما الـ Latest يبقى MAJOR جديد (زي 7 لـ 8)، اقرا "Migration guide" أو الـ Changelog الأول، وحدّث Package واحد في كل commit. وأدوات زي **Dependabot** على GitHub بتعمل Pull Request لكل تحديث لوحدها، والـ CI يجرّبه (كتاب Git فصل 17).
:::

:::tip[ملخص الفصل]
- MAJOR.MINOR.PATCH = بيكسر . ميزة . إصلاح.
- `^` = نفس الـ MAJOR (الافتراضي)، و`~` = نفس الـ MINOR، ومن غير رمز = بالظبط.
- مع `0.x` الـ `^` بتبقى أضيق، والـ Prerelease مش بتيجي إلا لو طلبتها.
- الـ Lockfile بيسجل النسخة و resolved و integrity لكل Package. ارفعه على Git ومتمسحوش.
- `npm ci` للـ CI (صارم ويمسح node\_modules)، و`npm install` للشغل العادي، و`npm update` للتحديث جوه الـ Range.
- `npm outdated`: Current / Wanted / Latest.
:::

### صح ولا غلط؟

1. `^2.4.1` بيقبل 2.9.0.
2. `~2.4.1` بيقبل 2.5.0.
3. `npm update` بيغيّر الـ Range المكتوب في package.json.
4. `npm ci` بيشتغل من غير package-lock.json.

### أسئلة مراجعة

1. ارجع للغز بتاع سارة. إيه اللي حصل غالباً؟ وإزاي الـ Lockfile كان هيمنعه؟
2. `^0.4.2` يقبل 0.5.0؟ ليه؟
3. في `npm outdated`، إمتى الـ Wanted يبقى أقل من الـ Latest؟
4. ليه سيرفر الـ Deploy المفروض يستخدم `npm ci` مش `npm install`؟

### تحديات الفصل

<small>جرّبها بإيدك، والحلول في ملحق الإجابات.</small>

1. **[سهل]** شغّل `npm outdated` على أي مشروع قديم عندك، وفسّر كل صف.
2. **[متوسط]** بـ `npx semver -r` اتأكد من إجاباتك على أسئلة الصح والغلط فوق.
3. **[صعب]** في مشروع تجربة: غيّر Range في package.json بإيدك لنسخة MAJOR تانية، وشغّل `npm ci` وشوف الـ Error، وبعدين صلّحه بالطريقة الصح وقارن الـ Lockfile قبل وبعد بـ `git diff`.
