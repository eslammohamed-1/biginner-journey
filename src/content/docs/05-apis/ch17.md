<small>المرحلة 5 · تصميم REST</small>

الـ Status code بيقول «حصل إيه» بشكل عام. بس الـ Client محتاج يعرف بالظبط: أنهي Field غلط؟ أعمل إيه؟ وكل API كان بيخترع شكل لوحده. هنا هنشوف الفوضى دي على GitHub و Stripe بجد، وبعدين الـ Standard اللي حلها: application/problem+json، Field بـ Field، ونقرا الـ Errors من الـ Client صح، ونحمي السيرفر من إنه يطلّع أسراره.

:::note[بعد الفصل ده هتكون عارف]
- الفوضى: GitHub و Stripe وكل واحد بشكل
- application/problem+json: الـ Fields الخمسة
- type هو المفتاح، و about:blank وقاعدة الـ title
- الـ Extensions: errors\[\] بـ pointer لكل Field
- قراية الـ Problem من الـ Client بـ type مش بـ detail
- الـ 500: متطلّعش Stack trace، ورجّع ID للـ Logs
- Checklist لأي Error بتصممه
:::

<a id="s17-1"></a>

## 17.1 كل API بلغة

جربنا نغلط في 2 من أشهر الـ APIs:

```sh title="Terminal"
$ curl -s https://api.github.com/repos/expressjs/nope-nope -H 'User-Agent: book'
{"message":"Not Found","documentation_url":"https://docs.github.com/rest/repos/repos#get-a-repository","status":"404"}

$ curl -s https://api.stripe.com/v1/charges -u sk_test_abc:
{
  "error": {
    "message": "Invalid API Key provided: sk_test_abc",
    "type": "invalid_request_error"
  }
}
```

GitHub: `message` فوق، و`status` **String**. Stripe: كله جوه `error`، و`type` كلمة. وغيرهم `{"error": "..."}` أو `{"errors": [...]}` أو `{"msg": ...}`. وكانت المشكلة إن أي Client (أو مكتبة، أو أداة Monitoring) لازم يتعلم شكل جديد مع كل API. فاتطور حل: **RFC 7807** سنة 2016، واتحدّث بـ **RFC 9457** سنة 2023: شكل واحد لأي Error في أي HTTP API.

<a id="s17-2"></a>

## 17.2 الشكل

```http title="رد من library.js"
HTTP/1.1 404 Not Found
Content-Type: application/problem+json
"type": "https://example.com/problems/article-not-found"
"title": "Article not found"
"status": 404
"detail": "No article with id '999'"
"instance": "urn:uuid:f4c6…"
```

1. `HTTP/1.1 404 Not Found`: نوع Content خاص بيقول "ده Problem". الـ Client يعرف من الهيدر قبل ما يقرا الـ Body.
2. `"type": "https://example.com/problems/article-not-found"`: <strong>أهم Field.</strong> URI بيحدد نوع المشكلة، والكود بيقرّر على أساسه. لو فتحته المفروض يوديك صفحة Docs بتشرح المشكلة. ولو مش موجود = `about:blank`.
3. `"title": "Article not found"`: ملخص قصير للإنسان، **ثابت لنفس الـ type** (ميتغيرش من مرة للتانية).
4. `"status": 404`: نسخة من الـ Status code (Number مش String زي GitHub)، علشان لو حد عدّى الـ JSON لوحده يفضل فاهم.
5. `"detail": "No article with id '999'"`: شرح **المرة دي بالذات** للإنسان، ويساعده يصلّح. الكود **ميعملش Parse** للنص ده أبداً.
6. `"instance": "urn:uuid:f4c6…"`: (اختياري) URI لـ "الحدوتة دي بالذات"، زي ID تقدر تدوّر بيه في الـ Logs.

```sh title="Terminal"
$ curl -s localhost:3001/v1/articles/999
{"type":"https://example.com/problems/article-not-found","title":"Article not found","status":404,"detail":"No article with id '999'"}
```

:::caution[about:blank ليه قاعدة]
لو الـ `type` هو `about:blank`، يبقى المشكلة "مفيش عنها حاجة غير الـ Status code"، والـ RFC بيقول الـ `title` **المفروض** يبقى نفس الجملة الرسمية للكود ("Not Found" لـ 404). أول نسخة من `library.js` كانت بترجّع `about:blank` مع `"title": "Article not found"`، وده مخالف. فصلّحناها: أي مشكلة ليها معنى خاص أخدت `type` خاص بيها، و`about:blank` فضل للحاجات العامة:
:::

```sh title="Terminal"
$ curl -s localhost:3001/v1/nothing
{"type":"about:blank","title":"Not Found","status":404,"detail":"No route for GET /v1/nothing"}
$ curl -s -X POST localhost:3001/v1/articles --json @/tmp/big.json
{"type":"about:blank","title":"Content Too Large","status":413,"detail":"request entity too large"}
```

**المصادر الرسمية:** [RFC 9457 · Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html) · [IANA · HTTP Problem Types registry](https://www.iana.org/assignments/http-problem-types/http-problem-types.xhtml)

<a id="s17-3"></a>

## 17.3 الـ Extensions: errors لكل Field

الـ RFC بيسمحلك تزوّد أي Fields تانية (Extensions) حسب الـ `type`. وأشهرها لمشاكل الـ Validation: قايمة `errors`، كل واحد فيه `detail` و`pointer` (JSON Pointer للـ Field، فصل 7 و 15). الـ RFC نفسه بيدّي المثال ده (وبيكتب الـ Pointer بالشكل `"#/age"`)، واحنا استخدمنا الشكل `"/title"`:

```sh title="Terminal"
$ curl -s -X POST localhost:3001/v1/articles --json '{"title":"Hi","status":"live"}'
```

```json
{
  "type": "https://example.com/problems/validation",
  "title": "Validation failed",
  "status": 422,
  "errors": [
    { "pointer": "/title",    "detail": "Too small: expected string to have >=3 characters" },
    { "pointer": "/status",   "detail": "Invalid option: expected one of \"draft\"|\"review\"|\"published\"" },
    { "pointer": "/authorId", "detail": "Invalid input: expected string, received undefined" }
  ]
}
```

الـ 3 مشاكل في رد واحد، فالفورم في React يقدر يحط كل رسالة تحت الـ Input بتاعها مرة واحدة، بدل ما المستخدم يصلّح غلطة ويكتشف التانية. والرسايل دي طالعة من zod (اللي شفناه في فصل 7) ومحولة لـ Pointers بسطرين في `library.js`.

:::note[Extensions شائعة]
`errors` (Validation)، و`traceId` أو `instance` (للـ Logs)، و`retryAfter`، و`balance` (المثال اللي في الـ RFC: "رصيدك 30 والمطلوب 50"). والـ Client اللي ميعرفش Extension **يتجاهلها**.
:::

<a id="s17-4"></a>

## 17.4 قراية الـ Problem من الـ Client

نكمّل على `ApiError` بتاع فصل 10. القاعدة: <strong>قرّر بالـ `type`</strong>، واعرض الـ `detail` للإنسان، ومتعملش أبداً `if (p.detail.includes("not found"))` لأن النص ممكن يتغير أو يتترجم.

```js title="problem.mjs"
const res = await fetch(BASE + path, init);
const type = res.headers.get("content-type") ?? "";
if (res.ok) return res.status === 204 ? null : res.json();
if (type.includes("application/problem+json")) {
  const p = await res.json();
  switch (p.type) {                  // stable machine key
    case "https://example.com/problems/validation":
      for (const e of p.errors) console.log(`  field ${e.pointer}: ${e.detail}`);
      break;
    case "https://example.com/problems/article-not-found":
      console.log("  show a 'not found' page");
      break;
    default:
      console.log(`  ${p.status} ${p.title}${p.detail ? " — " + p.detail : ""}`);
  }
}
```

```sh title="Terminal"
$ node problem.mjs
POST bad article:
  field /title: Too small: expected string to have >=3 characters
  field /authorId: Invalid input: expected string, received undefined
GET missing article:
  show a 'not found' page
POST publish twice:
  409 Already published — Article '6' is already published
```

## 17.5 الـ 500: اللي ميطلعش برّه

في `library.js` عملنا Route بيضرب Error فيه "سر" (باسورد Database وهمي). Express 5 بيمسك الـ Error من الـ `async` handler لوحده ويوديه للـ Error middleware:

```sh title="Terminal"
$ curl -si localhost:3001/v1/debug/crash
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json; charset=utf-8

{"type":"about:blank","title":"Internal Server Error","status":500,"instance":"urn:uuid:f4c64429-270c-43b2-a87f-7172512af3b6"}
```

```sh title="الـ Log بتاع السيرفر (مش للـ Client)"
! f4c64429-270c-43b2-a87f-7172512af3b6 Error: DB password=hunter2 rejected
!     at file:///workspace/book7/lab/library.js:201:9
!     at Layer.handleRequest (.../node_modules/router/lib/layer.js:152:17)
```

#### اللي راح للـ Client

"حصل خطأ عندنا"، و ID. مفيش رسالة الـ Error، ولا Stack trace، ولا أسماء ملفات. الـ RFC نفسه بيحذّر من إن الـ Stack dump يطلع برّه.

#### اللي راح للـ Log

كل حاجة، ومعاها نفس الـ ID. المستخدم يبعتلك الـ ID في الـ Support، وانت تدوّر عليه في الـ Logs وتلاقي المشكلة بالظبط.

## 17.6 Checklist لأي Error

1. الـ Status code صح (فصل 16)، ومش 200 أبداً.
2. `Content-Type: application/problem+json`.
3. `type` ثابت لكل نوع مشكلة، وصفحة Docs ليه. والكود بتاع الـ Client بيعتمد عليه.
4. `title` ثابت، و`detail` بيساعد المستخدم يصلّح ("العنوان لازم 3 حروف على الأقل")، مش بيشرح الكود بتاعك.
5. Validation = كل الأخطاء مرة واحدة في `errors` بـ `pointer`.
6. 429 و 503: `Retry-After`. و 401: `WWW-Authenticate`. و 405: `Allow`.
7. 500: من غير أسرار، وبـ ID يربط بالـ Log.
8. متكشفش معلومات: "الإيميل ده مش مسجل" في Login بتساعد اللي بيخمّن الحسابات. قول "الإيميل أو الباسورد غلط".

:::tip[ملخص الفصل]
- كل API كان بشكل (GitHub و Stripe مختلفين)، و RFC 9457 وحّد الشكل.
- `application/problem+json` وفيه `type` و`title` و`status` و`detail` و`instance`.
- `type` هو اللي الكود بيقرر بيه. و `about:blank` = الـ title هو جملة الكود الرسمية.
- Extensions زي `errors[]` بـ `pointer` لكل Field.
- الـ 500: ID للـ Client، والتفاصيل في الـ Log بس.
:::

### صح ولا غلط؟

1. الـ Client يقدر يعتمد على نص `detail` علشان يعرف نوع المشكلة.
2. لو الـ `type` مش موجود في الـ Problem، قيمته الافتراضية `about:blank`.
3. إنك تبعت الـ Stack trace في الـ 500 بيساعد الـ Client وده Best practice.

### أسئلة مراجعة

1. ليه الـ `status` موجود في الـ Body مع إنه في الـ Status line؟
2. إيه الفرق بين `title` و`detail`؟ وأنهي واحد ثابت؟
3. اكتب Problem لـ "رصيدك مش كفاية" بـ Extension مناسب.
4. ليه بنرجّع ID في الـ 500؟
