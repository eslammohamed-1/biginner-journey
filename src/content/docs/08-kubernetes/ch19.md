<small>المرحلة 6 · التشغيل الاحترافي</small>

لما فريق كامل بيشتغل على نفس الـ Cluster، مش منطقي كل واحد يبقى معاه صلاحية يمسح أي حاجة. الـ RBAC هو نظام الصلاحيات اللي بيحدد مين يقدر يعمل إيه، وفين.

:::note[بعد الفصل ده هتكون عارف]
- يعني إيه RBAC وليه مهم
- الـ Role والـ RoleBinding جوه Namespace
- الـ ClusterRole والـ ClusterRoleBinding
- الـ verbs والـ resources والـ apiGroups
- الـ ServiceAccount للـ Pods
- التأكد من الصلاحيات بـ kubectl auth can-i
:::

<a id="s19-1"></a>

## 19.1 إيه هي الـ RBAC؟ مين يقدر يعمل إيه جوه الـ Namespace؟

الـ <strong>RBAC (Role-Based Access Control)</strong> ده نظام الصلاحيات. بنقسمه لخطوتين:

#### Role

بنحدد فيها إيه الأفعال المسموح بيها جوه الـ Namespace دي.

#### RoleBinding

بنربط الـ Role دي بأشخاص حقيقيين (الموظفين) أو بـ ServiceAccounts.

تخيلها كده: الـ Role هي "الكارنيه" اللي مكتوب عليه مسموح يدخل أنهي أوض، والـ RoleBinding هو إنك تسلّم الكارنيه ده لشخص معين.

:::note[معلومة مهمة]
الـ RBAC في Kubernetes "مسموح فقط" (additive): مفيش قواعد "ممنوع". أي حاجة مش مسموحة صراحةً تبقى ممنوعة.
:::

<a id="s19-2"></a>

## 19.2 الـ Role بالتفصيل <small>(إضافة)</small>

```yaml title="pod-reader-role.yaml"
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
```

1. `apiVersion: rbac.authorization.k8s.io/v1`: الـ Role دايماً تبع Namespace واحدة (هنا `dev`)، وصلاحياتها جوهها بس.
2. `rules:`: الـ `""` (فاضي) = الـ core group اللي فيه pods و services و configmaps و secrets. للـ Deployments بتكتب `"apps"`.
3. `resources: ["pods", "pods/log"]`: على أنهي Objects. `pods/log` اسمها subresource وهي اللي بتسمح بـ `kubectl logs`.
4. `verbs: ["get", "list", "watch"]`: الأفعال المسموحة: هنا قراية بس.

**الـ verbs الأساسية وبتقابل أنهي أمر**

| الـ verb | المعنى | مثال أمر |
|---|---|---|
| `get` | قراية Object واحد بالاسم | `kubectl get pod web` |
| `list` | عرض الكل | `kubectl get pods` |
| `watch` | متابعة التغييرات لايف | `kubectl get pods -w` |
| `create` | إنشاء | `kubectl create / apply` |
| `update` / `patch` | تعديل | `kubectl edit / apply / scale` |
| `delete` | مسح | `kubectl delete` |
| `*` | كل الأفعال (استخدمها بحذر) |   |

<a id="s19-3"></a>

## 19.3 الـ RoleBinding <small>(إضافة)</small>

```yaml title="read-pods-binding.yaml"
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: ahmed
  apiGroup: rbac.authorization.k8s.io
- kind: ServiceAccount
  name: app-sa
  namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

1. `apiVersion: rbac.authorization.k8s.io/v1`: لازم في نفس الـ Namespace بتاعة الـ Role.
2. `subjects:`: الـ `subjects` = مين هياخد الصلاحية: User أو Group أو ServiceAccount.
3. `roleRef:`: أنهي Role هنربطها. الـ `roleRef` مينفعش يتعدّل بعد الإنشاء؛ لو عايز تغيره امسح الـ Binding واعمله تاني.

:::note[مين هو الـ User؟]
Kubernetes معندوش Object اسمه User. المستخدمين بيتعرّفوا من برّه، عن طريق شهادات أو OIDC (زي Google أو Azure AD). الـ RBAC بيستقبل الاسم بس ويطبّق عليه القواعد.
:::

<a id="s19-4"></a>

## 19.4 ClusterRole و ClusterRoleBinding <small>(إضافة)</small>

**Namespace مقابل Cluster**

|   | Role / RoleBinding | ClusterRole / ClusterRoleBinding |
|---|---|---|
| النطاق | Namespace واحدة | الـ Cluster كله |
| Objects مش تبع Namespace | مينفعش | ينفع (nodes, pv, namespaces) |
| مثال | مطوّر يقرا الـ Pods في dev | فريق Ops يشوف الـ Nodes كلها |

:::tip[Trick مفيد]
ممكن تعمل **ClusterRole** مرة واحدة وتربطه بـ **RoleBinding** في كل Namespace لوحدها، فالصلاحية تتطبق جوه الـ Namespace دي بس. وKubernetes جاي معاه ClusterRoles جاهزة زي `view` و `edit` و `admin` و `cluster-admin`.
:::

**تشريح الأمر**

```sh
kubectl create rolebinding dev-view --clusterrole=view --user=ahmed -n dev
```

1. `create rolebinding dev-view`: اعمل RoleBinding اسمه `dev-view`.
2. `--clusterrole=view`: اربطه بالـ ClusterRole الجاهز `view` (قراية لكل حاجة ما عدا الـ Secrets). ولو Role عادية: `--role=pod-reader`.
3. `--user=ahmed`: الـ subject. وفيه كمان `--group=` و `--serviceaccount=dev:app-sa` (namespace:name).
4. `-n dev`: في الـ Namespace دي، فالصلاحية جوه dev بس.

<a id="s19-5"></a>

## 19.5 الـ ServiceAccount: هوية الـ Pod <small>(إضافة)</small>

الـ Users للبشر، أما الـ **ServiceAccount** فهي هوية للـ Pods نفسها لما تحتاج تكلم الـ API Server (زي أداة CI/CD أو Operator). كل Namespace فيها ServiceAccount اسمه `default`، وأي Pod من غير ما تحدد بياخده.

```sh title="Terminal"
kubectl create serviceaccount app-sa -n dev
```

```yaml title="pod · serviceAccountName"
spec:
  serviceAccountName: app-sa    # الـ Pod هيشتغل بصلاحيات app-sa
  containers:
  - name: app
    image: my-app:1.0
```

<a id="s19-6"></a>

## 19.6 اتأكد من الصلاحيات: kubectl auth can-i <small>(إضافة)</small>

**تشريح الأمر**

```sh
kubectl auth can-i delete pods -n dev --as=ahmed
```

1. `auth can-i`: اسأل الـ API Server: "أقدر أعمل كذا؟" والرد `yes` أو `no`.
2. `delete pods`: الـ verb وبعده الـ resource.
3. `-n dev`: في أنهي Namespace.
4. `--as=ahmed`: اسأل كأنك المستخدم ده (Impersonation)، ومحتاجة إنت نفسك تكون Admin. وللـ ServiceAccount: `--as=system:serviceaccount:dev:app-sa`.

```sh title="Terminal"
$ kubectl auth can-i list pods -n dev --as=ahmed
yes
$ kubectl auth can-i delete pods -n dev --as=ahmed
no
$ kubectl auth can-i --list -n dev --as=ahmed     # كل الصلاحيات
```

:::tip[Least Privilege]
إدّي كل حد أقل صلاحية يقدر يشتغل بيها. ابدأ بـ `view`، وزوّد لما يكون فيه احتياج حقيقي. وابعد عن `cluster-admin` إلا للضرورة.
:::

:::tip[ملخص الفصل]
- الـ Role = إيه المسموح، والـ RoleBinding = لمين. وجوه Namespace واحدة.
- الـ ClusterRole/ClusterRoleBinding للـ Cluster كله وللـ Objects اللي مش تبع Namespace.
- القاعدة = apiGroups + resources + verbs.
- الـ ServiceAccount هوية للـ Pods، وبتتحدد بـ `serviceAccountName`.
- `kubectl auth can-i` بيختبر الصلاحية قبل ما تتفاجئ.
:::

### أسئلة مراجعة

1. إيه الفرق بين Role و ClusterRole؟
2. ليه `apiGroups: [""]` فاضي في قاعدة الـ pods؟
3. عايز مطوّر يشوف الـ logs بس في Namespace واحدة، تكتب إيه في الـ resources والـ verbs؟
4. إزاي تتأكد إن ServiceAccount معين يقدر يعمل list للـ secrets؟

### صح ولا غلط؟

1. الـ RBAC فيه قواعد "ممنوع" صريحة.
2. ينفع تربط ClusterRole بـ RoleBinding في Namespace واحدة.
3. Kubernetes فيه Object اسمه User بتعمله بـ kubectl create user.
