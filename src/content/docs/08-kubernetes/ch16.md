:::note[إضافة]

الـ Container بطبيعته مؤقت: لو اتمسح أو اتعمله Restart، أي ملف اتكتب جواه بيضيع. طب لو عندي Database؟ الفصل ده بيشرح إزاي نخلّي البيانات تعيش أطول من الـ Pod، من أبسط Volume لحد التخزين الدائم PV و PVC.

:::note[بعد الفصل ده هتكون عارف]
- ليه البيانات بتضيع من الـ Container
- الفرق بين volumes و volumeMounts
- emptyDir و hostPath وإمتى أستخدم كل واحد
- الـ PersistentVolume والـ PersistentVolumeClaim
- الـ StorageClass والـ accessModes والـ reclaimPolicy
- فكرة سريعة عن الـ StatefulSet
:::

<a id="s16-1"></a>

## 16.1 المشكلة: الـ Container ذاكرته قصيرة

فاكر في فصل الـ DaemonSet لما قولنا إن الـ Pod محتاج ياخد ملفات من الـ Node، فاستخدمنا `volumeMounts` جوه الـ containers و `volumes` جوه الـ spec؟ دي كانت أول مرة نشوف الـ Volumes. تعالى نفهمها كويس.

الـ File System بتاع الـ Container بيتولد معاه ويموت معاه. لو الـ Container وقع والـ kubelet قومه تاني، هيقوم "نضيف" كأنه أول مرة. ده كويس لـ Web Server، بس كارثة لـ Database!

الـ **Volume** ببساطة هو "فولدر" بيتركّب (mount) جوه الـ Container من برّه، فالبيانات اللي بتتكتب فيه متتمسحش مع الـ Container.

#### volumes (في الـ Pod spec)

بتعرّف فيها **مصدر** التخزين: جاي منين؟ (فولدر على الـ Node، مساحة مؤقتة، Disk دائم، ConfigMap ...).

#### volumeMounts (في الـ container)

بتحدد هتركّب الـ Volume ده **فين جوه الـ Container** (الـ mountPath)، بالاسم.

<a id="s16-2"></a>

## 16.2 أنواع الـ Volumes الأساسية

**أشهر أنواع الـ Volumes**

| النوع | البيانات بتعيش لحد إمتى؟ | بيستخدم في إيه؟ |
|---|---|---|
| `emptyDir` | طول ما الـ Pod موجود (بتعدّي الـ Restart بتاع الـ Container، بس بتتمسح مع الـ Pod) | مساحة مشتركة بين Containers في نفس الـ Pod، Cache مؤقت |
| `hostPath` | على الـ Node نفسها (لو الـ Pod راح Node تانية مش هيلاقيها) | الـ DaemonSets اللي بتقرأ ملفات الـ Node زي `/var/log` |
| `configMap` / `secret` | مع الـ Object نفسه | تركيب ملفات إعدادات (الفصول الجاية) |
| `persistentVolumeClaim` | دائمة، مستقلة عن الـ Pod والـ Node | Databases وأي بيانات مهمة |

### مثال: emptyDir بين اتنين Containers

```yaml title="shared-pod.yaml"
apiVersion: v1
kind: Pod
metadata:
  name: shared-pod
spec:
  volumes:
  - name: shared-data
    emptyDir: {}
  containers:
  - name: writer
    image: busybox
    command: ["sh", "-c", "while true; do date >> /data/log.txt; sleep 5; done"]
    volumeMounts:
    - name: shared-data
      mountPath: /data
  - name: web
    image: nginx
    volumeMounts:
    - name: shared-data
      mountPath: /usr/share/nginx/html
```

1. `apiVersion: v1`: عرّفنا Volume اسمه `shared-data` من نوع `emptyDir`. الـ `{}` معناها "من غير إعدادات إضافية".
2. `containers:`: الـ Container الأول بيكتب التاريخ كل 5 ثواني في `/data/log.txt`. الـ `>>` معناها "ضيف في آخر الملف" من غير ما تمسح القديم.
3. `- name: web`: الـ Container التاني شايف نفس الفولدر بس في مسار تاني، فـ nginx هيعرض الملف اللي الأول بيكتبه.

:::note[معلومة مهمة]
الربط بين `volumes` و `volumeMounts` بيتم **بالاسم** (`name: shared-data`). لو الاسم مختلف حرف واحد، الـ Pod هيرفض يتعمل.
:::

<a id="s16-3"></a>

## 16.3 التخزين الدائم: PV و PVC

الـ hostPath مربوط بـ Node واحدة، والـ emptyDir بيموت مع الـ Pod. عشان كده Kubernetes فصل الموضوع لطرفين، زي "شقة" و"عقد إيجار":

#### PersistentVolume (PV)

الشقة نفسها: مساحة تخزين حقيقية في الـ Cluster (Disk على Cloud، NFS ...). بيعملها الـ Admin أو بتتعمل أوتوماتيك.

#### PersistentVolumeClaim (PVC)

عقد الإيجار: الـ Pod (أو إنت) بتطلب "عايز 5Gi تخزين بالمواصفات دي"، وKubernetes يدوّر على PV مناسب ويربطهم (Bound).

#### StorageClass

شركة المقاولات: بدل ما الـ Admin يعمل PVs بإيده، الـ StorageClass بيعمل PV جديد أوتوماتيك لكل PVC (Dynamic Provisioning).

![الـ Pod بيطلب بالـ PVC، والـ PVC بيرتبط بـ PV بيمثل الـ Disk الحقيقي.](./assets/ch16-fig1.png)

*الـ Pod بيطلب بالـ PVC، والـ PVC بيرتبط بـ PV بيمثل الـ Disk الحقيقي.*

### الـ PVC

```yaml title="db-pvc.yaml"
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-pvc
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: standard
  resources:
    requests:
      storage: 5Gi
```

1. `apiVersion: v1`: طلب تخزين اسمه `db-pvc`.
2. `spec:`: طريقة الوصول (شوف الجدول تحت). `ReadWriteOnce` = قراءة وكتابة من Node واحدة.
3. `storageClassName: standard`: اسم الـ StorageClass. على minikube اسمه `standard` (شوفه بـ `kubectl get storageclass`).
4. `resources:`: المساحة المطلوبة: 5 GiB.

### استخدام الـ PVC جوه Pod

```yaml title="postgres-pod.yaml"
spec:
  containers:
  - name: db
    image: postgres:16
    env:
    - name: POSTGRES_PASSWORD
      value: "secret"          # في الحقيقة استخدم Secret (فصل 18)
    volumeMounts:
    - name: db-data
      mountPath: /var/lib/postgresql/data
  volumes:
  - name: db-data
    persistentVolumeClaim:
      claimName: db-pvc        # اسم الـ PVC اللي عملناه
```

دلوقتي لو مسحت الـ Pod وعملته تاني، البيانات هتفضل موجودة لأنها في الـ PV مش في الـ Container.

**الـ accessModes**

| الـ Mode | الاختصار | المعنى |
|---|---|---|
| `ReadWriteOnce` | RWO | قراءة وكتابة من Node واحدة بس (الأشهر، أغلب Disks الـ Cloud) |
| `ReadOnlyMany` | ROX | قراءة بس من Nodes كتير |
| `ReadWriteMany` | RWX | قراءة وكتابة من Nodes كتير (محتاج تخزين بيدعمه زي NFS) |
| `ReadWriteOncePod` | RWOP | Pod واحدة بس في الـ Cluster كله |

**الـ reclaimPolicy: إيه اللي يحصل للـ PV لما الـ PVC يتمسح؟**

| القيمة | المعنى |
|---|---|
| `Delete` | الـ PV والـ Disk يتمسحوا (الافتراضي في الـ Dynamic Provisioning). خلّي بالك! |
| `Retain` | الـ PV يفضل موجود بالبيانات، والـ Admin يتصرف فيه يدوي. الأأمن للـ Production. |

**تشريح الأمر**

```sh
kubectl get pv,pvc -A
```

1. `get`: اعرض Objects.
2. `pv,pvc`: نوعين مع بعض مفصولين بفاصلة من غير مسافة، فبيعرض الـ PVs والـ PVCs في أمر واحد.
3. `-A`: اختصار `--all-namespaces`: من كل الـ Namespaces. (الـ PV نفسه مش تبع أي Namespace، بس الـ PVC تبع).

```sh title="Terminal"
$ kubectl get pvc
NAME     STATUS   VOLUME                 CAPACITY   ACCESS MODES   STORAGECLASS   AGE
db-pvc   Bound    pvc-3f1c...            5Gi        RWO            standard       40s
```

:::caution[STATUS = Pending]
لو الـ PVC فاضل `Pending`، يبقى مفيش PV مناسب ولا StorageClass تقدر تعمل واحد. اعمل `kubectl describe pvc db-pvc` وشوف الـ Events.
:::

## 16.4 لمحة عن الـ StatefulSet <small>(إضافة)</small>

الـ Deployment بيعامل الـ Pods كأنهم نسخ متطابقة ممكن تستبدل أي واحد بأي واحد. ده مش مناسب لـ Database cluster لأن كل Pod ليه "هوية" وبيانات خاصة بيه. الـ **StatefulSet** بيدي كل Pod:

- اسم ثابت ومرتب: `db-0`، `db-1`، `db-2`.
- PVC خاص بيه (عن طريق `volumeClaimTemplates`) بيفضل مربوط بيه حتى لو اتعمله Restart على Node تانية.
- تشغيل وإيقاف بالترتيب، و DNS ثابت لكل Pod عن طريق Headless Service.

```yaml title="statefulset.yaml (مختصر)"
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db          # Headless Service (clusterIP: None)
  replicas: 3
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
      - name: db
        image: postgres:16
        volumeMounts:
        - { name: data, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:    # كل Pod ياخد PVC لوحده
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 5Gi
```

:::tip[ملخص الفصل]
- الـ Container مؤقت، والـ Volume هو اللي بيحفظ البيانات برّه.
- `volumes` = المصدر (في الـ Pod)، و `volumeMounts` = مكان التركيب (في الـ Container)، والربط بالاسم.
- `emptyDir` بيعيش مع الـ Pod، `hostPath` مع الـ Node، والـ PVC دائم.
- الـ PVC طلب، الـ PV تخزين حقيقي، والـ StorageClass بيعمل PVs أوتوماتيك.
- الـ StatefulSet للتطبيقات اللي كل Pod فيها ليه هوية وبيانات خاصة.
:::

### أسئلة مراجعة

1. إيه الفرق بين `volumes` و `volumeMounts`؟
2. ليه الـ hostPath مش مناسب لـ Database في Cluster فيه أكتر من Node؟
3. الـ PVC حالته Pending، تعمل إيه؟
4. إمتى تختار `Retain` بدل `Delete`؟

### صح ولا غلط؟

1. البيانات في emptyDir بتفضل موجودة بعد مسح الـ Pod.
2. الـ ReadWriteOnce معناها Pod واحدة بس في الـ Cluster كله.
3. الـ StatefulSet بيدي كل Pod اسم ثابت زي db-0.
