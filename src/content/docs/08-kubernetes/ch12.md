الـ Deployment معمول لحاجة المفروض تفضل شغالة على طول، زي موقع أو API. طب لو عندي شغلانة تتعمل مرة وتخلص، زي Backup أو Migration أو إرسال تقرير؟ هنا بييجي دور الـ Job، ولو عايزها تتكرر على مواعيد يبقى CronJob.

:::note[بعد الفصل ده هتكون عارف]
- الفرق بين Job و Deployment
- الـ completions والـ parallelism والـ backoffLimit
- كتابة CronJob وفهم الـ schedule
- تنضيف الـ Jobs القديمة
:::

## 12.1 يعني إيه Job؟

تخيل إنك عايز تعمل Backup للـ Database. لو حطيته في Deployment، أول ما الـ Backup يخلص والـ Container يقفل، الـ Deployment هيفتكره وقع ويقومه تاني، ويفضل يعمل Backup ورا Backup للأبد! المشكلة إن الـ Deployment فاكر إن "الطبيعي" إن الحاجة تفضل شغالة.

الـ **Job** عكسه: الطبيعي عنده إن الـ Pod يخلص شغله ويقفل بنجاح (exit code 0). لو فشل يعيد المحاولة، ولو نجح يقف ويقول "خلصت".

```yaml title="job.yaml"
apiVersion: batch/v1
kind: Job
metadata:
  name: db-backup
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 3
  activeDeadlineSeconds: 600
  ttlSecondsAfterFinished: 3600
  template:
    spec:
      restartPolicy: OnFailure
      containers:
      - name: backup
        image: postgres:16
        command: ["sh", "-c", "pg_dump -h db -U app appdb > /backup/db.sql"]
```

1. `apiVersion: batch/v1`: الـ Jobs في الـ API group اسمه `batch/v1`.
2. `spec:`: لازم الشغلانة تنجح كام مرة عشان الـ Job يعتبر نفسه خلص (الـ Default 1).
3. `parallelism: 1`: كام Pod يشتغلوا في نفس الوقت (الـ Default 1).
4. `backoffLimit: 3`: لو فشل، يحاول كام مرة قبل ما يستسلم ويعلن فشل الـ Job (الـ Default 6).
5. `activeDeadlineSeconds: 600`: أقصى وقت للـ Job كله. لو عدّاه يتقفل ويعتبر فشل.
6. `ttlSecondsAfterFinished: 3600`: امسح الـ Job والـ Pods بتاعته أوتوماتيك بعد ساعة من ما يخلص.
7. `template:`: لازم تكون `OnFailure` أو `Never`، لأن `Always` (بتاعة الـ Deployment) مش مسموحة هنا.
8. `containers:`: الأمر اللي هيتنفذ. `sh -c` معناها "نفّذ النص ده كأمر shell"، عشان علامة `>` (احفظ الناتج في ملف) تشتغل.

```sh title="Terminal · توضيح للناتج"
$ kubectl apply -f job.yaml
job.batch/db-backup created
$ kubectl get jobs
NAME        STATUS     COMPLETIONS   DURATION   AGE
db-backup   Complete   1/1           12s        30s
$ kubectl get pods
NAME              READY   STATUS      RESTARTS   AGE
db-backup-x7k2m   0/1     Completed   0          30s
```

لاحظ إن الـ STATUS بتاعة الـ Pod بقت `Completed` مش Running، والـ READY `0/1`، وده الطبيعي لـ Job خلص.

| الأمر | بيعمل إيه |
|---|---|
| `kubectl logs job/db-backup` | الـ logs بتاعة الـ Pod اللي الـ Job عمله. |
| `kubectl describe job db-backup` | تفاصيل ومحاولات الفشل في الـ Events. |
| `kubectl delete job db-backup` | تمسح الـ Job والـ Pods بتاعته. |

#### completions: 5 و parallelism: 1

5 مرات ورا بعض، Pod Pod. مفيد لو عندك 5 دفعات بيانات لازم تتعالج بالترتيب.

#### completions: 5 و parallelism: 5

5 Pods في نفس الوقت. أسرع، بس بيستهلك موارد أكتر.

## 12.2 الـ CronJob: Job على مواعيد

لو عايز الـ Backup يتعمل كل يوم الساعة 2 بالليل، مش هتصحى كل يوم تعمل `kubectl apply`. الـ **CronJob** بيعمل Job جديد أوتوماتيك على الـ schedule اللي تحدده، بنفس فكرة الـ cron في Linux.

:::note[فاكر الـ cron؟]
صيغة الـ `schedule` هي نفس الخمس خانات بتاعة الـ cron اللي شرحناها في كتاب الـ Terminal (فصل 12): دقيقة، ساعة، يوم الشهر، الشهر، يوم الأسبوع. فـ `"0 2 * * *"` = كل يوم الساعة 2:00.
:::

```yaml title="cronjob.yaml"
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"
  timeZone: "Africa/Cairo"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: backup
            image: postgres:16
            command: ["sh", "-c", "pg_dump -h db -U app appdb > /backup/db.sql"]
```

1. `apiVersion: batch/v1`: نفس الـ API group.
2. `spec:`: الميعاد: كل يوم الساعة 2:00 الصبح (شوف التشريح تحت).
3. `timeZone: "Africa/Cairo"`: المنطقة الزمنية. لو مكتبتهاش هيستخدم توقيت الـ Cluster (غالباً UTC).
4. `concurrencyPolicy: Forbid`: لو الـ Job اللي فات لسه مخلصش، متبدأش واحد جديد. (`Allow` الـ Default، و `Replace` يوقف القديم ويبدأ الجديد).
5. `successfulJobsHistoryLimit: 3`: احتفظ بآخر 3 Jobs نجحوا وآخر واحد فشل، والباقي يتمسح.
6. `jobTemplate:`: `jobTemplate` = نفس الـ spec بتاع الـ Job اللي فوق بالظبط.

**تشريح الأمر**

```text
0 2 * * *
```

1. `0`: الدقيقة (0 لـ 59).
2. `2`: الساعة (0 لـ 23).
3. `*`: يوم الشهر (1 لـ 31). علامة `*` = أي قيمة (كل يوم).
4. `* `: الشهر (1 لـ 12).
5. `*`: يوم الأسبوع (0 لـ 6، والـ 0 = الأحد).

**أمثلة schedules**

| الـ schedule | معناه |
|---|---|
| `*/15 * * * *` | كل 15 دقيقة (`/` = كل كام). |
| `0 * * * *` | كل ساعة على رأس الساعة. |
| `30 9 * * 0-4` | 9:30 الصبح من الأحد للخميس (`-` = من لـ). |
| `0 0 1 * *` | أول كل شهر الساعة 12 بالليل. |

| الأمر | بيعمل إيه |
|---|---|
| `kubectl get cronjobs` | الـ CronJobs، ومعاها آخر مرة اشتغلت (LAST SCHEDULE). |
| `kubectl create job test-run --from=cronjob/nightly-backup` | شغّل الـ CronJob دلوقتي حالاً للتجربة من غير ما تستنى الميعاد. |
| `kubectl patch cronjob nightly-backup -p '{"spec":{"suspend":true}}'` | وقّف الـ CronJob مؤقتاً (`patch` بيعدّل حقل واحد، و `-p` فيه التعديل بصيغة JSON). |

:::caution[خلي بالك]
الـ CronJob ممكن (نادراً) يشغّل نفس الميعاد مرتين أو يفوّته لو الـ Cluster كان واقع. عشان كده خلي الشغلانة **Idempotent**، يعني لو اتنفذت مرتين النتيجة متبوظش (زي إن الـ Backup يكتب على نفس الملف بدل ما يكرر البيانات).
:::

:::tip[ملخص الفصل]
- الـ Deployment لحاجة تفضل شغالة، والـ Job لحاجة تخلص وتقفل.
- الـ Job: `completions` و `parallelism` و `backoffLimit`، و `restartPolicy` لازم OnFailure أو Never.
- الـ CronJob بيعمل Jobs على schedule بصيغة cron (دقيقة ساعة يوم شهر يوم-أسبوع).
- `concurrencyPolicy: Forbid` يمنع التداخل، و `ttlSecondsAfterFinished` للتنضيف.
:::

### أسئلة مراجعة

1. ليه مينفعش تعمل الـ Backup بـ Deployment؟
2. اكتب schedule لـ CronJob يشتغل كل يوم جمعة الساعة 11 بالليل.
3. Job فشل 3 مرات و `backoffLimit: 3`، إيه اللي هيحصل؟
4. إزاي تجرّب CronJob دلوقتي من غير ما تستنى ميعاده؟

### صح ولا غلط؟

1. ينفع تكتب `restartPolicy: Always` في Job.
2. `*/5 * * * *` معناها كل 5 دقايق.
3. الـ Pod بتاع Job اللي خلص بيبقى STATUS بتاعه Completed.
