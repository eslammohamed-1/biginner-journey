<small>المرحلة 1 · الأساسيات</small>

خلينا نشوف تطبيق عملي بسيط على كل اللي فات ده. طبعاً إحنا هنجرب على VM بسيطة، فهتكون هي الـ Node بتاعتنا وهتكون شايلة الـ Cluster كله، يعني الـ Control node والـ Worker node هيبقوا على نفس الـ VM.

:::note[بعد الفصل ده هتكون عارف]
- تسطيب Docker و kubectl و minikube على Ubuntu
- تشغيل Cluster بـ minikube start
- عمل Pod من ملف YAML
- عمل Pod من Image جاهزة بـ kubectl run
- قراية خانات READY و STATUS
:::

<a id="s4-1"></a>

## 4.1 (1) خلينا نسطّب Kubernetes

هنستخدم نسخة مصغرة من Kubernetes عشان نطبق عليها، ألا وهي **minikube**، بتكون عبارة عن fake cluster جواه Node واحدة شايلة الـ Cluster كله.

:::caution[على الماك: 3 أوامر بس]
الخطوات اللي تحت مكتوبة لسيرفر Ubuntu (بـ `apt`، مدير الحزم بتاع Ubuntu زي brew عندنا). على الماك مش محتاجها، وده المقابل:

```sh title="macOS"
brew install --cask docker     # Docker Desktop (افتحه مرة وسيبه شغال)
brew install kubectl minikube  # الأداتين
minikube start --driver=docker # شغّل الـ Cluster جوه Docker
```

وبعد كده كل أوامر `kubectl` و `minikube` في الكتاب زي ما هي بالظبط. والـ `moaz@Linux:~$` اللي في الأمثلة مجرد شكل الـ Prompt على جهاز الكاتب.
:::

1. **Update System & Install Dependencies**

   ```sh title="Step 1"
   sudo apt update && sudo apt upgrade -y
   sudo apt install -y curl wget apt-transport-https
   ```

   **تشريح الأمر**

   ```sh
   sudo apt install -y curl wget apt-transport-https
   ```

   1. `sudo`: نفّذ الأمر بصلاحيات الـ root (الأدمن).
   2. `apt`: مدير الحزم (Package Manager) في Ubuntu/Debian.
   3. `install`: نزّل وسطّب الحزم اللي بعده.
   4. `-y`: جاوب "yes" أوتوماتيك على أي سؤال تأكيد.
   5. `curl wget apt-transport-https`: أسامي الحزم: أدوات تنزيل من النت، ودعم الـ repositories اللي على https.

   وفي السطر الأول: `&&` معناها "نفّذ الأمر اللي بعدي **بس لو** اللي قبلي نجح"، و `apt update` بيحدّث قايمة الحزم، و `apt upgrade` بيرقّي الحزم المتسطبة.
2. **Install Docker** (هيبقى الـ Driver بتاع minikube)

   ```sh title="Step 2"
   sudo apt install -y docker.io
   sudo systemctl enable docker
   sudo systemctl start docker
   # Allow your user to run docker without sudo
   sudo usermod -aG docker $USER
   newgrp docker
   ```

   **تشريح الأمر**

   ```sh
   sudo usermod -aG docker $USER
   ```

   1. `usermod`: أمر بيعدّل بيانات User موجود.
   2. `-aG`: اختصار `-a -G`: ضيف (append) الـ User على Group، من غير ما تشيله من الـ Groups اللي هو فيها.
   3. `docker`: اسم الـ Group اللي أعضاؤه يقدروا يكلموا Docker من غير sudo.
   4. `$USER`: متغير (Variable) فيه اسم الـ User الحالي. علامة `$` معناها "هات قيمة المتغير ده".

   و `systemctl enable` بيخلي Docker يشتغل مع كل boot، و `start` بيشغّله دلوقتي. و `newgrp docker` بيفعّل الـ Group الجديد في الـ Terminal الحالي من غير logout. وأي سطر بيبدأ بـ `#` ده تعليق (Comment) مش بيتنفذ.
3. **Install kubectl** (الـ CLI بتاع Kubernetes)

   ```sh title="Step 3"
   curl -LO "https://dl.k8s.io/release/$(curl -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
   sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
   # To Verify =>  kubectl version --client
   ```

   **تشريح الأمر**

   ```sh
   curl -LO "https://dl.k8s.io/release/$(curl -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
   ```

   1. `curl`: أداة بتنزّل حاجة من URL.
   2. `-LO`: `-L`: لو الرابط بيحوّل (redirect) لرابط تاني امشي وراه. `-O`: احفظ الملف بنفس اسمه اللي في الرابط.
   3. `$(`: بداية **Command Substitution**: نفّذ الأمر اللي جوه الأقواس الأول، وحط الناتج بتاعه مكانه في النص.
   4. `curl -s https://dl.k8s.io/release/stable.txt`: الأمر الداخلي: بيجيب رقم آخر نسخة مستقرة (زي `v1.31.0`). و `-s` يعني silent من غير progress bar.
   5. `/bin/linux/amd64/kubectl`: باقي المسار: نسخة Linux لمعالجات amd64 (لو جهازك ARM غيّرها لـ `arm64`).

   **تشريح الأمر**

   ```sh
   sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
   ```

   1. `install`: بينسخ الملف ويظبط صلاحياته في خطوة واحدة.
   2. `-o root`: صاحب الملف (owner) هيبقى root.
   3. `-g root`: الـ Group بتاع الملف root.
   4. `-m 0755`: الصلاحيات: صاحبه يقرا ويكتب وينفّذ، والباقي يقروا وينفّذوا بس.
   5. `kubectl /usr/local/bin/kubectl`: من فين لفين: الملف اللي نزّلناه، للمكان اللي الـ Terminal بيدوّر فيه على الأوامر.
4. **Install Minikube**

   ```sh title="Step 4"
   curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
   sudo install minikube-linux-amd64 /usr/local/bin/minikube
   # To Verify => minikube version
   ```

## 4.2 (2) نشغّل الـ Cluster اللي نزّلناه

```sh title="Terminal"
minikube start --driver=docker
```

لما نـ run الأمر ده هيبني Cluster لأول مرة ويستخدم Docker كـ Driver يشغّل بيه الـ Cluster. لكن بعد كده لما نـ run الأمر ده تاني، فهو هيعيد تشغيل نفس الـ Cluster اللي قومناه في الأول، وحتى لو غيرت الـ Driver مش هيقوم Cluster جديد مختلف عن القديم، بل هيطلعلك رسالة خطأ، لأن دي مش الطريقة اللي بيسمح بيها minikube إنك تعمل أكتر من Cluster، وإنما بالطريقة دي:

```sh title="Terminal"
minikube start --profile cluster-1-name --driver=docker
minikube start --profile cluster-2-name --driver=docker
```

**تشريح الأمر**

```sh
minikube start --profile cluster-1-name --driver=docker
```

1. `minikube`: الأداة اللي بتعمل Cluster محلي للتجربة.
2. `start`: قوّم الـ Cluster (أو اعمله لو مش موجود).
3. `--profile cluster-1-name`: اسم الـ Cluster ده. كل profile = Cluster منفصل. لو مكتبتهوش الاسم الافتراضي `minikube`.
4. `--driver=docker`: شغّل الـ Node جوه Docker Container. علامة `=` بتربط الـ flag بقيمته، وينفع تكتبها بمسافة بدلها.

:::caution[خلي بالك]
ولكن ده مش مفضّل ولا محتاجينه حالياً في مرحلة التعلم، كمان إن الـ VM ليها حدود، فكتر الـ Clusters ممكن يعمل مشكلة.
:::

| الأمر | بيعمل إيه |
|---|---|
| `minikube status` | تتأكد إن الـ Cluster شغال. |
| `kubectl get nodes` | هتلاقي Node واحدة اسمها `minikube` حالتها `Ready`. |
| `minikube stop` | توقف الـ Cluster من غير ما تمسحه. |
| `minikube delete` | تمسح الـ Cluster خالص وتبدأ من الأول. |

## 4.3 (3) نجرب نعمل كام Pod

عندنا كذا طريقة:

### الطريقة الأولى: ملف YAML

نعمل ملف ونكتب فيه الـ Configuration بتاعة الـ Pod اللي عايزين نعمله (`pod.yaml`):

:::note[أول ملف YAML]
كل ملفات Kubernetes مكتوبة بـ YAML. لو القواعد مش واضحة (المسافات، و `key: value`، والشرطة `-`)، ارجع لصفحة YAML في كتاب APIs و JSON (فصل 21). وأشهر Error في الأول سببه مسافة زيادة أو ناقصة.
:::

```yaml title="pod.yaml"
apiVersion: v1
kind: Pod
metadata:
  name: single-container-pod
spec:
  containers:
  - name: nginx
    image: nginx:latest
    ports:
    - containerPort: 80
```

1. `apiVersion: v1`: نسخة الـ API ونوع الـ Object اللي بنعمله.
2. `metadata:`: اسم الـ Pod اللي هنتعامل بيه معاه.
3. `spec:`: المواصفات: Container اسمه nginx، من الـ Image دي، وبيسمع على 80.

:::caution[خلي بالك من المسافات]
الـ YAML حساس جداً للـ Indentation. استخدم **Spaces** مش Tabs، وخلي كل مستوى بمسافتين. أي مسافة غلط هتديك Error أو هتخلي الحقل يتقري في مكان غلط.
:::

نشغّل الملف ونستنى لحد ما الـ Pod تقوم (بنعرف ده من اللي مكتوب في خانة **STATUS**)، ونقدر نعرف عدد الـ Containers اللي جواه من **READY**: العدد اللي شغال فعلياً / العدد الكلي.

```sh title="Terminal · توضيح للناتج"
$ kubectl apply -f pod.yaml
pod/single-container-pod created
$ kubectl get pods
NAME                   READY   STATUS              RESTARTS   AGE
single-container-pod   0/1     ContainerCreating   0          10s
$ kubectl get pods
NAME                   READY   STATUS              RESTARTS   AGE
single-container-pod   0/1     ContainerCreating   0          19s
$ kubectl get pods
NAME                   READY   STATUS    RESTARTS   AGE
single-container-pod   1/1     Running   0          26s
```

**تشريح الأمر**

```sh
kubectl apply -f pod.yaml
```

1. `kubectl`: الـ CLI اللي بيكلم الـ API Server.
2. `apply`: طبّق الحالة اللي في الملف: لو الـ Object مش موجود اعمله، ولو موجود حدّثه بالفرق.
3. `-f`: اختصار `--filename`: اقرا من الملف (أو الفولدر أو الـ URL) اللي بعدي.
4. `pod.yaml`: اسم الملف اللي فيه الـ Configuration.

**تشريح الأمر**

```sh
kubectl get pods
```

1. `get`: اعرض قايمة بالـ Objects.
2. `pods`: نوع الـ Object. ينفع تكتبه `pod` أو `po` اختصار.

**أعمدة `kubectl get pods`**

| العمود | معناه |
|---|---|
| `NAME` | اسم الـ Pod. |
| `READY` | عدد الـ Containers الجاهزة / العدد الكلي جوه الـ Pod. |
| `STATUS` | المرحلة: `Pending` (مستني Node)، `ContainerCreating` (بينزّل الـ Image ويجهّز)، `Running`، `Completed`، `CrashLoopBackOff` (بيقع ويقوم ويقع). |
| `RESTARTS` | الـ Container عمل restart كام مرة. لو بيزيد يبقى فيه مشكلة. |
| `AGE` | من إمتى الـ Pod اتعمل (s ثواني، m دقايق، h ساعات، d أيام). |

### الطريقة التانية: Image جاهزة

نشغّل الـ Pod اعتماداً على Image جاهزة (نسخة جاهزة للتجربة زي busybox في Docker):

```sh title="Terminal · توضيح للناتج"
$ kubectl run my-pod --image=nginx
pod/my-pod created
$ kubectl get pods
NAME                   READY   STATUS              RESTARTS   AGE
my-pod                 0/1     ContainerCreating   0          4s
single-container-pod   1/1     Running             0          3m14s
$ kubectl get pods
NAME                   READY   STATUS    RESTARTS   AGE
my-pod                 1/1     Running   0          31s
single-container-pod   1/1     Running   0          3m41s
```

**تشريح الأمر**

```sh
kubectl run my-pod --image=nginx
```

1. `run`: اعمل Pod واحد على طول من الـ Terminal.
2. `my-pod`: اسم الـ Pod.
3. `--image=nginx`: الـ Image اللي الـ Container هيتعمل منها. لو مكتبتش tag هيستخدم `latest`.

:::note[معلومة مهمة]
- ولكن الطريقتين دول مش حاجة عملية ولا هما اللي بنستخدمهم في الشغل العملي، لأنهم بياخدوا وقت ومش طرق احترافية، وإنما للتجربة والتدريب فقط.
- الطريقة العملية إننا بننقل المحتوى اللي جوه الملف (`pod.yaml`) لملف تاني أكبر منه بيكون فيه حاجات أكتر عن الـ Pods ألا وهو (`deployment.yaml`).
- خلينا نتكلم أكتر عن إزاي نعمل Configurations أكتر للـ Pods في ملف (`pod.yaml`)، وبعدها نبقى نشوف إزاي المحتوى ده هيتنقل لملف (`deployment.yaml`).
:::

### أوامر هتحتاجها مع أي Pod

| الأمر | بيعمل إيه |
|---|---|
| `kubectl get pods -o wide` | الـ Pods ومعاها الـ IP والـ Node اللي شغالة عليها. |
| `kubectl describe pod my-pod` | كل التفاصيل، وأهم جزء فيها الـ **Events** في الآخر. |
| `kubectl logs my-pod` | الـ logs بتاعة الـ Container. |
| `kubectl exec -it my-pod -- sh` | تدخل جوه الـ Container وتفتح shell. |
| `kubectl delete pod my-pod` | تمسح الـ Pod (أو `kubectl delete -f pod.yaml`). |

**تشريح الأمر**

```sh
kubectl exec -it my-pod -- sh
```

1. `exec`: نفّذ أمر جوه Container شغال.
2. `-it`: `-i` (interactive): خلي الـ input مفتوح عشان تكتب. `-t` (tty): اعمل terminal حقيقي. الاتنين مع بعض = shell تفاعلي.
3. `my-pod`: اسم الـ Pod. لو جواه أكتر من Container ضيف `-c name`.
4. `--`: فاصل: أي حاجة بعده مش flags لـ kubectl، دي الأمر اللي هيتنفذ جوه الـ Container.
5. `sh`: الأمر نفسه: افتح shell. اكتب `exit` عشان تخرج.

**تشريح الأمر**

```sh
kubectl get pods -o wide
```

1. `-o`: اختصار `--output`: شكل الناتج.
2. `wide`: أعمدة زيادة (IP والـ Node). قيم تانية: `yaml` و `json` و `name` و `jsonpath=...`.

:::tip[ملخص الفصل]
- minikube بيعمل Cluster فيه Node واحدة للتجربة، وبيستخدم Docker كـ Driver.
- `minikube start` بيقوم نفس الـ Cluster كل مرة، ولو عايز أكتر من Cluster استخدم `--profile`.
- `kubectl apply -f pod.yaml` بيعمل Pod من ملف، و `kubectl run` من Image جاهزة.
- READY = الشغال فعلاً / الكلي، و STATUS بتقولك الـ Pod في أنهي مرحلة.
- في الشغل الحقيقي مش بنعمل Pods لوحدها، بنستخدم Deployment.
:::

### أسئلة مراجعة

1. إيه الأمر اللي بيقوم Cluster تاني بـ minikube؟
2. لو READY مكتوب فيها `1/2` ده معناه إيه؟
3. اكتب أمر يعمل Pod اسمه `web` من Image اسمها `nginx:1.27`.
4. ليه الطريقتين اللي جربناهم مش هما اللي بنستخدمهم في الشغل؟

### صح ولا غلط؟

1. في minikube الـ Control Plane والـ Worker على نفس الـ Node.
2. ينفع تستخدم Tabs في ملفات YAML.
3. `kubectl describe` بيوريك الـ Events بتاعة الـ Pod.
