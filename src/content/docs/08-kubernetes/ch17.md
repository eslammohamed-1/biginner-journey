<small>المرحلة 5 · البيانات والإعدادات</small>

في خلال كتابتك للـ YAML Files هتحتاج قيم تـ configure بيها حاجات، والقيم دي مش ثابتة. الفصل ده بيشرح إزاي نجمّعها في مكان واحد اسمه ConfigMap، وإزاي الـ Pod ياخدها كـ Environment Variables أو كملفات.

:::note[بعد الفصل ده هتكون عارف]
- ليه نفصل الإعدادات عن الكود
- إنشاء ConfigMap بالأوامر وبالـ YAML
- استخدامه كـ env و envFrom
- تركيبه كملفات بالـ Volume
- إيه اللي يحصل لما أعدّل الـ ConfigMap
:::

<a id="s17-1"></a>

## 17.1 الفكرة: متغيرات في مكان واحد

في خلال كتابتك للـ YAML Files هتحتاج تستخدم قيم عشان تـ configure حاجة، ولكن القيم دي مش ثابتة دايماً، ممكن نحتاج نغيرها. فهل من المنطقي إني كل ما أحتاج أغير فيها أدخل على كل الـ YAML Files اللي مستخدم فيها القيم دي وأغيرها بإيدي؟ أكيد لا. الأحسن إني أخليهم عبارة عن Variables (متغيرات) عشان أقدر أغير القيم دي بسهولة... إزاي برضو؟

خلينا نتخيل معايا المتغيرات دي:

```text title="المتغيرات"
DB_HOST = "localhost"
LOG_LEVEL = "debug"
MAX_CONNECTIONS = "10"
```

بدل ما أعرّفهم جوه كل YAML File وأحط قيمهم جوه نفس الـ YAML، لا، أنا أعمل YAML File منفصل وليكن اسمه `var.yaml` مجمّع فيه كل القيم دي، ولما يكون في YAML File محتاج يستخدم قيم المتغيرات دي يكلم الـ YAML ده ياخدهم منه. بحيث لو غيرت في القيم دي في ملف `var.yaml` هبقى وفّرت مجهود إني أروح لكل الـ YAML Files وأغير بإيدي.

نفس الفكرة دي Kubernetes بيوفرهالنا بحاجة اسمها الـ **ConfigMap**.

:::note[التعريف]
الـ ConfigMap هو Object في Kubernetes بيخزن إعدادات التطبيق منفصلة عن الكود. بدل ما تـ hardcode القيم (تكتبها بنفسك بشكل ثابت) في الـ image، بتحطها في ConfigMap، والـ Pod بياخدها منه وقت التشغيل.
:::

### إيه أنواع الحاجات اللي ممكن أخزنها في الـ ConfigMap؟

- إعدادات البيئة (dev، staging، prod).
- الـ URLs وأسماء الـ hostnames.
- الـ Feature flags.
- ملفات config كاملة زي (`nginx.conf`، `app.properties`).

:::caution[خلي بالك]
الـ ConfigMap للحاجات **غير السرية** بس. الباسوردات والـ Tokens مكانها الـ Secret (الفصل الجاي). وحجم الـ ConfigMap الواحد أقصاه 1 MiB.
:::

<a id="s17-2"></a>

## 17.2 إنشاء ConfigMap من الـ Terminal

```sh title="Terminal"
kubectl create configmap <config-name> \
    --from-literal=<key>=<value>
# مثال
kubectl create configmap app-config \
    --from-literal=APP_COLOR=blue \
    --from-literal=APP_MOD=prod
```

**تشريح الأمر**

```sh
kubectl create configmap app-config --from-literal=APP_COLOR=blue \
```

1. `create configmap`: اعمل Object جديد من نوع ConfigMap (بشكل Imperative، من غير ملف YAML).
2. `app-config`: اسم الـ ConfigMap، وهو اللي الـ Pods هتنده بيه.
3. `--from-literal=`: "خد القيمة دي مكتوبة زي ما هي" في الأمر نفسه. ممكن تكررها أكتر من مرة لأكتر من متغير.
4. `APP_COLOR=blue`: الـ key قبل علامة `=` والـ value بعدها.
5. `\`: آخر السطر معناها "الأمر لسه مكمّل في السطر اللي تحت"، بس عشان القراءة. لازم متكونش بعدها أي مسافة.

### من ملف كامل

**تشريح الأمر**

```sh
kubectl create configmap nginx-conf --from-file=nginx.conf
```

1. `--from-file=`: خد ملف من جهازك وحطه جوه الـ ConfigMap.
2. `nginx.conf`: اسم الملف هيبقى هو الـ key، ومحتواه كله هو الـ value. ولو عايز key مختلف: `--from-file=default.conf=nginx.conf`.

```sh title="Terminal"
$ kubectl get configmap app-config -o yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_COLOR: blue
  APP_MOD: prod
```

<a id="s17-3"></a>

## 17.3 ConfigMap بالـ YAML <small>(إضافة)</small>

```yaml title="app-config.yaml"
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "localhost"
  LOG_LEVEL: "debug"
  MAX_CONNECTIONS: "10"
  app.properties: |
    color=blue
    mode=prod
```

1. `apiVersion: v1`: الـ ConfigMap تبع الـ `v1` زي الـ Pod، ومفيهوش `spec`.
2. `data:`: بدل الـ spec بنكتب `data`: أزواج key: value. القيم دايماً نصوص، فحط الأرقام بين علامات تنصيص.
3. `app.properties: |`: علامة `|` في YAML معناها "اللي جاي نص متعدد السطور زي ما هو". مفيد لملفات الـ config الكاملة.

<a id="s17-4"></a>

## 17.4 إزاي الـ Pod ياخد القيم؟ <small>(إضافة)</small>

### (1) متغير واحد بالاسم: valueFrom

```yaml title="pod · env"
    env:
    - name: LOG_LEVEL
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: LOG_LEVEL
```

1. `env:`: اسم الـ Environment Variable اللي هيظهر جوه الـ Container.
2. `valueFrom:`: "هات القيمة من ConfigMap اسمه `app-config`، من الـ key اللي اسمه `LOG_LEVEL`".

### (2) كل الـ keys مرة واحدة: envFrom

```yaml title="pod · envFrom"
    envFrom:
    - configMapRef:
        name: app-config
```

1. `envFrom:`: كل key في الـ ConfigMap بيبقى Environment Variable بنفس الاسم. أسهل، بس خلي بالك من تضارب الأسماء.

### (3) كملفات: Volume

```yaml title="pod · volume"
  containers:
  - name: web
    image: nginx
    volumeMounts:
    - name: conf
      mountPath: /etc/nginx/conf.d
  volumes:
  - name: conf
    configMap:
      name: nginx-conf
```

1. `containers:`: فولدر `/etc/nginx/conf.d` جوه الـ Container هيبقى فيه ملف لكل key.
2. `volumes:`: مصدر الـ Volume هو الـ ConfigMap `nginx-conf` (نفس فكرة الـ Volumes في الفصل اللي فات).

**تشريح الأمر**

```sh
kubectl exec my-pod -- printenv LOG_LEVEL
```

1. `exec my-pod`: نفّذ أمر جوه الـ Container بتاع الـ Pod `my-pod`.
2. `--`: فاصل: كل اللي بعده هو الأمر اللي هيتنفّذ جوه الـ Container، مش options لـ kubectl.
3. `printenv LOG_LEVEL`: اطبع قيمة المتغير، عشان تتأكد إن الـ ConfigMap وصل.

<a id="s17-5"></a>

## 17.5 لو عدّلت الـ ConfigMap، إيه اللي يحصل؟ <small>(إضافة)</small>

:::caution[دقة: التغيير مش دايماً بيوصل علطول]
- <strong>لو بتستخدمه كـ env أو envFrom:</strong> الـ Environment Variables بتتقري مرة واحدة وقت تشغيل الـ Container. التعديل **مش هيوصل** غير لما الـ Pods تتعمل من جديد، مثلاً بـ `kubectl rollout restart deployment/my-app`.
- <strong>لو بتستخدمه كـ Volume:</strong> الملفات بتتحدّث لوحدها بعد شوية (ممكن دقيقة أو أكتر)، بس التطبيق نفسه لازم يعيد قراية الملف.
- لو عامله `subPath` في الـ volumeMount، الملف مش بيتحدّث خالص.
:::

```sh title="Terminal"
kubectl edit configmap app-config              # تعديل مباشر في الـ Editor
kubectl apply -f app-config.yaml               # أو عدّل الملف واعمل apply
kubectl rollout restart deployment/my-app      # عشان الـ env يتقري من جديد
```

:::tip[ملخص الفصل]
- الـ ConfigMap بيفصل الإعدادات (غير السرية) عن الـ image.
- بيتعمل بـ `--from-literal` أو `--from-file` أو YAML فيه `data`.
- الـ Pod بياخده بـ `valueFrom.configMapKeyRef` أو `envFrom` أو كـ Volume.
- تعديل الـ ConfigMap مش بيوصل للـ env غير بعد Restart، لكن الـ Volume بيتحدّث لوحده.
:::

### أسئلة مراجعة

1. ليه منكتبش القيم مباشرة جوه الـ image أو الـ YAML بتاع كل Pod؟
2. إيه الفرق بين `env.valueFrom` و `envFrom`؟
3. عدّلت قيمة في ConfigMap والتطبيق لسه شايف القديمة، ليه؟ وإيه الحل؟

### صح ولا غلط؟

1. الـ ConfigMap مكان مناسب لباسورد الـ Database.
2. علامة `\` في آخر السطر معناها إن الأمر مكمّل في السطر اللي بعده.
3. في `--from-file=nginx.conf` اسم الملف بيبقى هو الـ key.
