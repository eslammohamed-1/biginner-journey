<small>المرحلة 5 · البيانات والإعدادات</small>

:::note[إضافة]
الشرح الأصلي ذكر الـ Secrets كعنوان بس، فالفصل ده إضافة بنفس الأسلوب.
:::

الـ Secret هو أخو الـ ConfigMap، بس معمول للحاجات اللي محدش المفروض يشوفها: باسوردات، Tokens، مفاتيح، شهادات TLS. الفصل ده بيشرح بيتعمل إزاي، وبيتستخدم إزاي، وإيه حدود الأمان بتاعه بصراحة.

:::note[بعد الفصل ده هتكون عارف]
- الفرق بين Secret و ConfigMap
- ليه base64 مش تشفير
- إنشاء Secret بالأوامر وبالـ YAML (data و stringData)
- استخدامه في الـ Pod كـ env وكملفات
- تأمين الـ Secrets بجد
:::

<a id="s18-1"></a>

## 18.1 يعني إيه Secret؟

نفس فكرة الـ ConfigMap بالظبط: keys و values الـ Pod بياخدها كـ env أو كملفات. الفرق إن Kubernetes بيتعامل معاه على إنه حساس: مش بيظهر في `kubectl describe`، وبيتخزن في الـ Node في الذاكرة (tmpfs) مش على الـ Disk، وتقدر تحدد بالـ RBAC مين يقدر يقراه.

:::caution[أهم معلومة في الفصل: base64 مش تشفير]
القيم جوه الـ Secret بتتكتب بـ **base64**، وده مجرد "ترميز" (encoding) عشان أي بيانات حتى لو Binary تتكتب كنص. أي حد يقدر يفكه في ثانية:

```sh title="Terminal"
$ echo -n 'S3cr3t!' | base64
UzNjcjN0IQ==
$ echo 'UzNjcjN0IQ==' | base64 -d
S3cr3t!
```

يعني اللي معاه صلاحية يقرا الـ Secret من الـ API، شايف الباسورد. الأمان الحقيقي بييجي من الـ RBAC والتشفير في الـ etcd (تحت).
:::

**تشريح الأمر**

```sh
echo -n 'S3cr3t!' | base64
```

1. `echo`: اطبع النص.
2. `-n`: من غير سطر جديد في الآخر. لو نسيتها، الـ base64 هيشفّر الـ newline معاه والباسورد هتبقى غلط!
3. `'S3cr3t!'`: النص بين علامات تنصيص مفردة، عشان الـ Shell ميفسّرش علامات زي `!` و `$`.
4. `|`: الـ Pipe: خد ناتج الأمر اللي على الشمال وابعته كمدخل للأمر اللي على اليمين.
5. `base64`: حوّل المدخل لـ base64. ومع `-d` (decode) بيرجّعه للأصل.

<a id="s18-2"></a>

## 18.2 إنشاء Secret من الـ Terminal

**تشريح الأمر**

```sh
kubectl create secret generic db-secret --from-literal=DB_PASSWORD='S3cr3t!'
```

1. `create secret`: اعمل Object من نوع Secret.
2. `generic`: نوع الـ Secret: عام (keys و values عادية). فيه أنواع تانية زي `tls` و `docker-registry`.
3. `db-secret`: اسم الـ Secret.
4. `--from-literal=`: زي الـ ConfigMap بالظبط: key=value. وkubectl هو اللي بيعمل base64 لوحده.

**تشريح الأمر**

```sh
kubectl create secret tls my-tls --cert=tls.crt --key=tls.key
```

1. `tls`: نوع مخصص للشهادات، بيتحفظ فيه key اسمه `tls.crt` وواحد `tls.key`. ده نفس النوع اللي الـ cert-manager بيعمله.
2. `--cert=`: مسار ملف الشهادة على جهازك.
3. `--key=`: مسار ملف المفتاح الخاص (Private Key).

:::note[معلومة مهمة]
لو بتعمل Pull لـ images من Registry خاص، فيه نوع `docker-registry`، وبتحطه في الـ Pod تحت `imagePullSecrets`.
:::

<a id="s18-3"></a>

## 18.3 Secret بالـ YAML

```yaml title="db-secret.yaml"
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  DB_PASSWORD: UzNjcjN0IQ==
stringData:
  DB_USER: admin
```

1. `apiVersion: v1`: `Opaque` هو النوع العام (نفس `generic` في الأمر).
2. `data:`: في `data` لازم تكتب القيمة **متحوّلة base64** بإيدك.
3. `stringData:`: في `stringData` تكتبها نص عادي، وKubernetes هيحوّلها لوحده. أسهل وأقل غلط.

:::caution[خلي بالك]
متعملش `git commit` لملف Secret فيه قيم حقيقية! استخدم أدوات زي **Sealed Secrets** أو **External Secrets Operator** (بيجيب القيم من Vault أو AWS Secrets Manager).
:::

<a id="s18-4"></a>

## 18.4 استخدام الـ Secret في الـ Pod

```yaml title="pod · secret"
    env:
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: DB_PASSWORD
    envFrom:
    - secretRef:
        name: db-secret
    volumeMounts:
    - name: creds
      mountPath: /etc/creds
      readOnly: true
  volumes:
  - name: creds
    secret:
      secretName: db-secret
```

1. `env:`: زي `configMapKeyRef` بالظبط، بس `secretKeyRef`. الـ Container بيشوف القيمة الأصلية (مفكوكة).
2. `envFrom:`: أو كل الـ keys مرة واحدة.
3. `volumeMounts:`: أو كملفات: `/etc/creds/DB_PASSWORD`. لاحظ إنها `secretName` مش `name`. والطريقة دي أأمن من الـ env لأن الـ env ممكن يظهر في الـ logs.

**تشريح الأمر**

```sh
kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d
```

1. `get secret db-secret`: هات الـ Secret ده.
2. `-o jsonpath=`: بدل الجدول، اطبع حقل واحد بس من الـ Object.
3. `'{.data.DB_PASSWORD}'`: المسار: جوه `data` هات `DB_PASSWORD`. النقطة الأولى = الـ Object نفسه.
4. `| base64 -d`: ابعت القيمة للـ base64 يفكها، فتشوف الباسورد الأصلي. (وده دليل إن أي حد معاه صلاحية get يقدر يشوفه).

<a id="s18-5"></a>

## 18.5 تأمين الـ Secrets بجد

1. <strong>RBAC:</strong> اسمح بـ `get` و `list` على الـ secrets للي محتاجها بس (الفصل الجاي).
2. <strong>Encryption at Rest:</strong> بشكل افتراضي الـ Secrets في الـ etcd متخزنة base64 بس. فعّل الـ `EncryptionConfiguration` في الـ API Server (أو KMS في الـ Cloud) عشان تتشفر فعلاً.
3. <strong>متطبعهاش:</strong> خلي بالك من الـ logs، والـ `kubectl get -o yaml` قدام حد.
4. <strong>Immutable:</strong> تقدر تحط `immutable: true` للـ Secrets أو الـ ConfigMaps اللي مش هتتغير، عشان محدش يعدّلها بالغلط.

:::tip[ملخص الفصل]
- الـ Secret زي الـ ConfigMap بس للبيانات الحساسة.
- الـ base64 ترميز مش تشفير، والأمان الحقيقي من الـ RBAC والـ Encryption at Rest.
- `data` بقيم base64، و `stringData` بنص عادي.
- بيتستخدم بـ `secretKeyRef` أو `secretRef` أو Volume بـ `secretName`.
:::

### أسئلة مراجعة

1. ليه الـ base64 مش بيحمي الباسورد؟
2. إيه الفرق بين `data` و `stringData`؟
3. ليه `echo -n` مهمة قبل الـ base64؟
4. اذكر طريقتين لتأمين الـ Secrets في الـ Cluster.

### صح ولا غلط؟

1. الـ Secrets متشفرة في الـ etcd بشكل افتراضي.
2. الـ Container بيشوف قيمة الـ Secret مفكوكة (مش base64).
3. النوع `tls` بيحتوي على `tls.crt` و `tls.key`.
