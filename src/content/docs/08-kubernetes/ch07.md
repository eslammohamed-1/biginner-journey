<small>المرحلة 3 · إدارة الـ Workloads</small>

أكيد أنا هيبقى عندي أكتر من Pod في الـ App بتاعي، إزاي هفرق أو أميز بينهم؟ بمعنى إني أعرّف Kubernetes الـ Pods الموجودة عشان لما أديله أمر يعمل حاجة على Pod معينة منهم يعرف يميزها ويشتغل عليها. الإجابة هي الـ Labels والـ Selectors.

:::note[بعد الفصل ده هتكون عارف]
- يعني إيه Label وشكلها key: value
- الفرق بين الـ name والـ Label
- يعني إيه Selector وبيتكتب فين
- الـ matchLabels و الفلترة بـ kubectl -l
:::

<a id="s7-1"></a>

## 7.1 (1) الـ Label

من اسمها كده، الـ **Label** شبه الـ Tag أو الـ Sticker اللي بنلزقه على أي حاجة ونكتب عليه وصف معين عشان نعرف نميّز الحاجة دي بسهولة.

الـ Label بتكون عبارة عن: `key: value`، وهدفها إنها تساعدنا نصنّف ونرتّب الـ Objects الموجودة في Kubernetes زي الـ Pods والـ Deployments والـ Services وغيرهم.

#### مجموعة الـ Backend

فمثلاً لو عندي كذا Pod شغالين كـ Backend، ممكن أحط عليهم كلهم Label بالشكل ده: `type: backend`. كده أي Pod عليها الـ Label دي هتبقى ضمن مجموعة الـ Backend.

#### تمييز أدق

ولو فيه Pod معينة مسؤولة عن خدمة الطباعة مثلاً، أقدر أضيف لها Label تانية: `service: print`. وبكده أقدر أميّزها عن باقي الـ Backend Pods.

بالنسبة للتسمية، فأنت حر تماماً تختار أي أسماء للـ Key أو الـ Value، مفيش أسماء إجبارية. المهم إنك تختار أسماء واضحة ومنظمة عشان تبقى فاهم الـ Objects بتاعتك بسهولة، وكمان عشان Kubernetes يقدر يتعامل معاها بشكل صحيح.

:::note[معلومة مهمة]
<strong>الـ Labels مش الغرض منها إنها تكون اسم أو ID للـ Pod، لكن الغرض منها التصنيف والتجميع.</strong> Kubernetes بيستخدمها بعد كده مع الـ Selectors عشان يختار مجموعة معينة من الـ Pods ويتعامل معاها، زي مثلاً لما Service تربط نفسها بمجموعة Pods معينة.
:::

### إيه هو Syntax الـ Labels؟

الـ Labels بتتكتب جوه الـ `metadata` اللي بتكون موجودة مع الـ `apiVersion` والـ `kind` والـ `spec`. الـ metadata غالباً بيكون فيها حاجتين مهمين: `name` و `labels`.

```yaml title="الشكل العام"
apiVersion: v1
kind: Pod
metadata:
  name: name_of_pod_itself
  labels:
    key_1: value_1
    key_2: value_2
```

```yaml title="مثال"
apiVersion: v1
kind: Pod
metadata:
  name: frontend-pod
  labels:
    environment: production
    app: website
```

<a id="s7-2"></a>

## 7.2 الفرق بين الـ name والـ Label

<strong>يعني إيه name؟</strong> هو الاسم اللي Kubernetes بيعرف بيه الـ Pod دي. ولما تيجي تتعامل مع الـ Pod عن طريق Kubernetes API أو أوامر `kubectl` هتستخدم الاسم ده. <strong>لازم كمان يكون الاسم فريد جوه نفس الـ Namespace.</strong>

:::note[مثال من الحياة]
عشان نفرق أكتر بين الـ name والـ label، خلينا ناخد مثال: لنفترض إنت موظف في شركة، ليك ID أو اسم خاص بيك، وفي نفس الوقت إنت تبع Team معين. هل لما بيتحوّلك المرتب الشركة هتبعته للـ Team كله ولا ليك أنت شخصياً؟؟ أكيد ليك أنت، باستخدام اسمك أو الـ ID بتاعك، لأن دي عملية موجهة لشخص واحد.

لكن لو الشركة عايزة تبعت email لكل أعضاء فريق معين أو تعمل اجتماع للـ Team، مش هتختار كل شخص بالاسم، لكنها هتحدد الـ Team كله وكل أعضائه هيتضمّنوا في العملية.
:::

**name مقابل labels**

|   | name | labels |
|---|---|---|
| **بيحدد** | Object واحد بعينه | مجموعة Objects ليهم نفس الصفة أو الدور |
| <strong>فريد؟</strong> | أيوه، جوه نفس الـ Namespace | لأ، نفس الـ Label على Objects كتير |
| **بنستخدمه في** | نتعامل مع Object مباشرة | نستهدفهم كلهم مرة واحدة |

<a id="s7-3"></a>

## 7.3 (2) الـ Selectors

من اسمها كده هي حاجة بتشاور أو بتختار الـ Labels اللي إنت عملتها وحطيتها على الـ Pods.

بمعنى إن عندك Object أو Service معينة بتحتاج تكلّم مجموعة الـ Pods بتوع الـ Backend مثلاً، هتروح جوه الـ Configuration file بتاع الـ Object أو الـ Service دي وتحدد الـ Labels اللي عايز تستهدفهم عن طريق الـ **Selector**. بتكون عبارة عن `key: value`، ولازم تكون بنفس الأسامي والقيم زي الـ Labels اللي إنت عملتها.

### إيه هو Syntax الـ Selector؟

الـ Selector بتتكتب جوه الـ `spec` اللي بتكون موجودة مع الـ `apiVersion` والـ `kind`:

```yaml title="الشكل العام"
apiVersion: v1
kind: Service
spec:
  selector:
    key_1: value_1   # same as label_1
    key_2: value_2   # same as label_2
```

```yaml title="مثال"
apiVersion: v1
kind: Service
spec:
  selector:
    environment: production
    app: website
```

![الـ Selector بيختار كل الـ Pods اللي عليها نفس الـ Label، واللي مش مطابق بيتجاهله.](./assets/ch07-fig1.png)

*الـ Selector بيختار كل الـ Pods اللي عليها نفس الـ Label، واللي مش مطابق بيتجاهله.*

:::note[إضافة: matchLabels]
الـ Service بتكتب الـ selector على طول (`key: value`). لكن الـ Objects الأحدث زي الـ Deployment والـ ReplicaSet والـ DaemonSet بتكتبه جوه `matchLabels`، وكمان تقدر تستخدم `matchExpressions` لشروط زي `In` و `NotIn`. هتشوفها في الفصول الجاية.

```yaml title="Deployment selector"
selector:
  matchLabels:
    app: website
```
:::

### الـ Labels من الـ Terminal

| الأمر | بيعمل إيه |
|---|---|
| `kubectl get pods --show-labels` | الـ Pods ومعاها كل الـ Labels. |
| `kubectl get pods -l app=website` | فلترة: الـ Pods اللي عليها الـ Label دي بس. |
| `kubectl get pods -l 'env in (dev,prod)'` | فلترة بشرط (set-based). |
| `kubectl label pod my-pod tier=backend` | إضافة Label لـ Pod موجودة. |
| `kubectl label pod my-pod tier-` | مسح الـ Label (علامة `-` في الآخر). |

**تشريح الأمر**

```sh
kubectl get pods -l 'env in (dev,prod)'
```

1. `-l`: اختصار `--selector`: فلتر بالـ Labels.
2. `env`: الـ key بتاع الـ Label.
3. `in (dev,prod)`: الشرط: القيمة تكون dev أو prod. وفيه كمان `notin`، و `!env` (الـ key مش موجود).
4. `'`: التنصيص عشان الـ shell ميفهمش الأقواس والمسافات غلط.

**تشريح الأمر**

```sh
kubectl label pod my-pod tier=backend --overwrite
```

1. `label`: ضيف أو عدّل Labels على Object موجود.
2. `pod my-pod`: النوع والاسم.
3. `tier=backend`: الـ Label بصيغة `key=value` (في الـ Terminal بـ `=` مش `:`).
4. `--overwrite`: لازم لو الـ key موجود قبل كده وعايز تغيّر قيمته، وإلا هيديك Error.

وعشان تمسح Label اكتب اسم الـ key وبعده علامة `-` لازقة فيه: `kubectl label pod my-pod tier-`.

:::tip[ملخص الفصل]
- الـ Label = `key: value` للتصنيف والتجميع، وبتتكتب في `metadata.labels`.
- الـ name فريد ويحدد Object واحد، والـ Labels بتجمع Objects كتير.
- الـ Selector بيختار الـ Objects بالـ Labels، وبيتكتب في `spec.selector`.
- الأسامي والقيم في الـ Selector لازم تطابق الـ Labels بالظبط (وحساسة لحالة الحروف).
:::

### أسئلة مراجعة

1. ليه منستخدمش الـ name عشان الـ Service تختار الـ Pods؟
2. اكتب الـ Labels لـ Pod تبع الـ backend في بيئة الـ staging.
3. Service الـ selector بتاعها `app: Web` والـ Pods عليها `app: web`، هتشتغل؟
4. اكتب أمر يعرض الـ Pods اللي عليها `tier=backend` بس.

### صح ولا غلط؟

1. ينفع اتنين Pods في نفس الـ Namespace يبقى ليهم نفس الـ name.
2. ينفع اتنين Pods يبقى عليهم نفس الـ Labels.
3. الـ Labels بتتكتب جوه الـ spec.
