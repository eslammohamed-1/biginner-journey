<small>المرحلة 5 · الشغل المنظّم</small>

بعد 3 شهور، هتفتح git log وتلاقي: update، fix، asdf، final، final2. مش هتعرف أي حاجة اتعملت فين. رسالة الـ Commit هي الملاحظة اللي بتكتبها لنفسك في المستقبل ولزمايلك. الفصل ده عن شكل الرسالة الكويسة، وصيغة Conventional Commits المنتشرة، وإزاي تقسّم شغلك لـ Commits مركّزة بـ git add -p.

:::note[بعد الفصل ده هتكون عارف]
- ليه رسالة الـ Commit مهمة وإيه شكل الرسالة الوحشة
- قواعد الرسالة الكويسة: عنوان قصير بصيغة الأمر وجسم بيشرح ليه
- صيغة Conventional Commits: الأنواع والـ Scope والـ Breaking change
- الـ Atomic commits: Commit واحد = تغيير واحد
- git add -p عشان تختار أجزاء من الملف
- إمتى تصلّح الرسايل وإمتى تسيبها
:::

<a id="s13-1"></a>

## 13.1 المشكلة: تاريخ مالوش معنى

تلات شهور بعد ما خلصت مشروع Bankist، حد بعتلك: "الـ Transfer بيقبل مبالغ بالسالب، والرصيد بيزيد!". فاكر إن الحتة دي كانت شغالة. فتحت `git log` عشان تعرف إمتى اتكسرت، ولقيت 40 Commit: تسعة منهم اسمهم `update`، وخمسة `fix`، وواحد `asdf` من ليلة كنت فيها تعبان. كل Commit لازم تفتحه وتقرا الـ diff بتاعه عشان تعرف عمل إيه. اللي كان المفروض ياخد دقيقة، أخد ساعة ونص.

الكود نفسه بيقول **إيه** اللي اتعمل. بس ليه اتعمل؟ وإمتى؟ وكان بيحل إيه؟ ده مكتوب في مكان واحد بس: رسالة الـ Commit. هي الملاحظة اللي بتسيبها لنفسك في المستقبل ولأي حد هيشتغل على المشروع، ولو اتكتبت وحش، مفيش حاجة تانية تعوّضها. قارن التاريخين دول:

#### تاريخ وحش

```sh title="Terminal"
$ git log --oneline
9f1c2ab update
3b7e0d1 fix
a12c9e4 more changes
77d0b3f asdf
c71f7c3 final
```

#### تاريخ محترم

```sh title="Terminal"
$ git log --oneline
9f1c2ab fix(form): show error on empty email
3b7e0d1 feat(form): add contact form
a12c9e4 style: format with prettier
77d0b3f docs: add setup steps to README
c71f7c3 feat: add home page
```

في التاني تقدر تعرف من غير ما تفتح ولا ملف: فين اتضافت الفورم، وإمتى اتصلح الـ Bug، وأنهي Commit مجرد Format (فتتجاهله وانت بتدوّر على Bug).

## 13.2 قواعد الرسالة الكويسة

معظم وقتك هتكتب الرسالة في سطر واحد بـ `-m`، وده تمام للحاجات الصغيرة. بس الرسالة الكاملة ليها شكل متعارف عليه من أيام مطوري Linux (اللي عملوا Git أصلاً)، والشكل ده مش ذوق: أدوات كتير معتمدة عليه. `git log --oneline` بيعرض أول سطر بس، و GitHub بيقص العنوان بعد 72 حرف، وصفحة الـ PR بتاخد العنوان والجسم من الـ Commit. وعشان تكتب رسالة كاملة، اعمل `git commit` من غير `-m`، والـ Editor هيفتح (افتكر [↩ 2.5](../ch02/#s2-5 "الـ Editor: افتح VS Code مش Vim")):

```gitignore title="رسالة Commit كاملة (في الـ Editor)"
fix(form): show error when email is empty

Submitting the form with an empty email used to
reload the page silently. Now we validate before
submit and show an inline message.
Closes #7
```

1. `fix(form): show error when email is empty`: <strong>العنوان:</strong> سطر واحد، حوالي 50 حرف (ومتعديش 72)، بصيغة الأمر (`add` مش `added`)، ومن غير نقطة في الآخر.
2. ``: <strong>سطر فاضي:</strong> لازم، عشان Git والأدوات تعرف فين العنوان وفين الجسم.
3. `Submitting the form with an empty email used to`: <strong>الجسم (اختياري):</strong> بيشرح **ليه** و**إيه**، مش "إزاي" (الكود بيقول إزاي). سطور حوالي 72 حرف.
4. `Closes #7`: <strong>Footer:</strong> ربط بـ Issue أو ملاحظات زي `BREAKING CHANGE:`.

:::tip[اختبار الجملة]
العنوان الكويس يكمّل الجملة دي: "<strong>If applied, this commit will ...</strong>". مثلاً: "will <em>add contact form</em>" ✓، "will <em>added stuff</em>" ✗. وده سبب صيغة الأمر. ولو مش عارف تكتب العنوان في سطر واحد، غالباً الـ Commit بيعمل حاجات كتير.
:::

:::note[لو حابب تتعمق: أدوات بتساعدك تكتب]
`git commit -v` (Verbose) بيعرض الـ diff كله تحت الرسالة في الـ Editor، فتكتب وانت شايف اللي عملته (السطور دي مش بتدخل الرسالة). و `git config --global commit.template ~/.gitmessage` بيخلي الـ Editor يفتح بقالب انت كاتبه (مثلاً أسماء الأنواع كتذكير). و `git log --grep="form"` بيدوّر في الرسايل، وهنا بتظهر قيمة الرسايل الكويسة. وفي الـ Footer فيه "Trailers" متعارف عليها زي `Co-authored-by: Ahmed <ahmed@mail.com>`، اللي GitHub بيعرض بيها الاتنين كأصحاب الـ Commit.
:::

:::note[عربي ولا إنجليزي؟]
الإنجليزي هو المتعارف عليه، وأسهل مع الأدوات والـ AI والشغل مع أي حد. لكن الأهم إنها تبقى واضحة ومتسقة: لو مشروع شخصي وبتكتب عربي أوضح لك، مفيش مشكلة تقنية.
:::

## 13.3 Conventional Commits

القواعد اللي فاتت بتخلي الرسالة مقروءة للبني آدمين. بس تخيل لو كمان **البرامج** تقدر تقراها: أداة تعدّي على الرسايل وتقولك "من آخر إصدار فيه 3 ميزات جديدة و 5 إصلاحات، يبقى الإصدار الجاي 1.4.0"، وتكتب صفحة التغييرات (Changelog) لوحدها. ده بالظبط اللي عملته مشاريع زي Angular، ومنها طلعت صيغة اتحولت لمواصفة رسمية اسمها **Conventional Commits** (الإصدار 1.0.0)، ودلوقتي منتشرة جداً في مشاريع JavaScript. وهتلاقي الـ AI نفسه لما تطلب منه رسالة Commit بيكتبها بالشكل ده. شكلها:

**تشريح الأمر**

```sh
feat(cart)!: change price format to cents
```

1. `feat`: الـ **Type**: نوع التغيير (الجدول تحت).
2. `(cart)`: الـ **Scope** (اختياري): الجزء اللي اتغير من المشروع، بين قوسين.
3. `!`: اختياري: **Breaking change**، يعني التغيير ده بيكسر حاجة كانت شغالة (لازم اللي بيستخدم الكود يعدّل حاجة).
4. `:`: نقطتين ومسافة بعد النوع.
5. `change price format to cents`: الوصف: بحروف صغيرة غالباً، وبصيغة الأمر.

**أنواع Conventional Commits**

| النوع | استخدامه | مثال |
|---|---|---|
| `feat` | ميزة جديدة للمستخدم | `feat: add dark mode toggle` |
| `fix` | إصلاح Bug | `fix: prevent negative balance` |
| `docs` | توثيق بس (README، تعليقات) | `docs: add deploy steps` |
| `style` | شكل الكود (مسافات، Format) من غير تغيير سلوك | `style: run prettier` |
| `refactor` | إعادة كتابة من غير تغيير السلوك | `refactor: extract calcInterest()` |
| `perf` | تحسين سرعة | `perf: debounce search input` |
| `test` | اختبارات | `test: add cases for transfer` |
| `build` | أدوات البناء والـ Dependencies | `build: upgrade vite` |
| `ci` | GitHub Actions وأخواتها | `ci: add lint workflow` |
| `chore` | صيانة مش داخلة في اللي فوق | `chore: update .gitignore` |
| `revert` | إلغاء Commit | `revert: feat: add dark mode` |

:::note[رسمياً فين؟]
المواصفة نفسها بتفرض `feat` و `fix` بس، والباقي متعارف عليه (من إعدادات commitlint المشهورة). وفايدتها مش الشكل بس: أدوات بتقرا الرسايل دي وتعمل منها **CHANGELOG** ورقم الإصدار أوتوماتيك (`fix` = Patch، `feat` = Minor، `!` = Major، الفصل 14).
:::

**تشريح الأمر**

```sh
git commit -m "feat(auth)!: require email verification" -m "BREAKING CHANGE: unverified users can no longer log in."
```

1. `git commit -m "..."`: العنوان بالصيغة: نوع و Scope و `!`.
2. `-m "BREAKING CHANGE: ..."`: التانية = فقرة الـ Footer. الكلمة `BREAKING CHANGE:` بحروف كبيرة دي جزء من المواصفة، وبتشرح إيه اللي اتكسر.

<a id="s13-4"></a>

## 13.4 Atomic commits: Commit واحد = تغيير واحد

يوم جمعة قعدت 4 ساعات على البورتفوليو: صلّحت Bug في الفورم، وضفت Footer، وعملت Format للملفات كلها، وحدّثت المكتبات. وفي الآخر `git add .` و Commit واحد. الأسبوع اللي بعده اكتشفت إن المكتبة الجديدة كسرت الـ Animation. عاوز تلغي التحديث بس بـ `git revert`؟ مينفعش: الـ revert هيلغي الأربع حاجات مع بعض، وانت عاوز إصلاح الفورم والـ Footer. هتقعد تفصل بإيدك.

الـ Commit الذري (Atomic) بيعمل **حاجة واحدة كاملة**: يتفهم لوحده، والمشروع شغال بعده، ولو عملتله revert بيشيل الحاجة دي بس.

#### ✗ Commit واحد

"fix form bug, add footer, format all files, update packages": لو الـ Footer عمل مشكلة، مينفعش تلغيه من غير ما تلغي إصلاح الفورم.

#### ✓ أربع Commits

`fix(form): ...` و `feat: add footer` و `style: format` و `build: update packages`. كل واحد يتفهم ويتلغي لوحده.

## 13.5 git add -p: اختار حتت من الملف

"تمام، Commit لكل حاجة" سهل لما كل حاجة في ملف لوحدها. بس الحياة مش كده: وانت بتصلّح Bug في `transfer()` في `app.js`، لاحظت إنك محتاج Function لتنسيق العملة، فكتبتها في آخر نفس الملف. دلوقتي الملف فيه تغييرين ملهمش علاقة ببعض.

طب لو في نفس الملف صلّحت Bug **و** ضفت حاجة جديدة؟ `git add file` هياخد الاتنين. الحل: `git add -p` بيعرضلك كل "حتة" (Hunk) اتغيرت ويسألك:

**تشريح الأمر**

```sh
git add -p app.js
```

1. `git add`: ضيف للـ Staging.
2. `-p`: Patch (أو `--patch`): اعرض التغييرات حتة حتة وأنا أختار.
3. `app.js`: اختياري: ملف معين. من غيره هيعدي على كل الملفات المتعدلة.

```sh title="Terminal"
$ git add -p app.js
@@ -10,6 +10,9 @@ function transfer(from, to, amount) {
+  if (amount <= 0) return false;
(1/2) Stage this hunk [y,n,q,a,d,s,e,?]? y
@@ -40,3 +43,8 @@
+function formatCurrency(value) {
(2/2) Stage this hunk [y,n,q,a,d,s,e,?]? n
```

**اختيارات git add -p**

| الحرف | معناه |
|---|---|
| `y` | Yes: ضيف الحتة دي |
| `n` | No: سيبها |
| `s` | Split: قسّمها لحتت أصغر (لو ينفع) |
| `e` | Edit: عدّلها بإيدك في الـ Editor (متقدم) |
| `a` / `d` | كل الحتت الجاية في الملف ده / ولا واحدة منهم |
| `q` | Quit: اخرج (اللي اخترته فاضل في الـ Staging) |
| `?` | المساعدة |

بعدها: `git diff --staged` تتأكد، و `git commit -m "fix: reject non-positive amounts"`، وبعدين `git add -p` تاني للباقي.

:::tip[حاجة مشتركة: -p = Patch]
الـ `-p` في Git غالباً = "اشتغل حتة حتة أو اعرض الـ Patch": `git add -p` و `git restore -p` (ارمي حتت معينة) و `git stash -p` و `git log -p` (اعرض الـ diff). وفي VS Code نفس الفكرة: تختار سطور في الـ diff وتعمل **Stage Selected Ranges**.
:::

:::tip[مفيد جداً مع الـ AI]
الـ AI عدّل 4 حاجات في ملف وانت عاوز 3 بس؟ `git add -p`: اختار الـ 3، Commit، وبعدين `git restore app.js` يرمي الرابعة. ده أحسن من إنك تقبل كله أو ترفض كله.
:::

## 13.6 صلّحت الرسالة؟ إمتى ينفع

عملت Commit ولسه دايس Enter، ولقيت الرسالة `fix: form bgu`. أو اكتشفت بعد يوم إن 3 Commits ورا بعض رسايلهم `wip`. ينفع تصلّح؟ الإجابة دايماً على نفس السؤال اللي شفناه في التراجع (الفصل 6): <strong>حد تاني شاف الـ Commit ده ولا لأ؟</strong> تعديل الرسالة بيعمل Commit جديد بـ Hash جديد (الرسالة جزء من اللي بيتحسب منه الـ Hash). فلو لسه عندك بس، اعمل اللي انت عاوزه. لو اتشارك، فكّر مرتين:

**تصليح رسايل الـ Commits**

| الموقف | الحل |
|---|---|
| آخر Commit، لسه ما اتبعتش | `git commit --amend` ([↩ 6.3](../ch06/#s6-3 "git commit --amend: صلّح آخر Commit")) |
| Commits أقدم، لسه ما اتبعتوش | `git rebase -i` و `reword` (الفصل 15) |
| اتبعتت على Branch عليه PR | مش مشكلة: Squash and merge هيخليك تكتب رسالة جديدة نضيفة |
| اتبعتت على main | سيبها، واتعلم للمرة الجاية. تعديل تاريخ main المشترك أسوأ من رسالة وحشة |

:::tip[ملخص الفصل]
- العنوان: قصير، بصيغة الأمر، من غير نقطة، وسطر فاضي قبل الجسم اللي بيشرح ليه.
- Conventional Commits: `type(scope)!: description`، والأنواع feat و fix و docs و style و refactor و test و chore...
- `BREAKING CHANGE:` أو `!` للتغييرات اللي بتكسر.
- Atomic: Commit واحد = تغيير واحد كامل.
- `git add -p`: y و n و s و q، تختار حتت من الملف.
:::

### صح ولا غلط؟

1. `style:` معناه تغيير في الـ CSS بس.
2. `git add -p` ممكن يضيف جزء من ملف ويسيب الباقي.
3. الأحسن تعدّل رسايل Commits قديمة على main بعد ما اتبعتت.

### أسئلة مراجعة

1. أعد كتابة الرسايل دي بـ Conventional Commits: "fixed bug in login"، "README"، "new navbar + changed colors".
2. ليه العنوان بصيغة الأمر؟
3. إمتى تستخدم `refactor` وإمتى `fix`؟
4. إيه فايدة الـ Atomic commits لما تحتاج `git revert`؟

### تحديات الفصل

<small>جرّبها بإيدك، والحلول في ملحق الإجابات.</small>

1. **[سهل]** اعمل 3 Commits في الـ playground بأنواع مختلفة (feat و docs و chore)، واعرضهم بـ `git log --oneline`.
2. **[متوسط]** عدّل ملف في مكانين بعاد عن بعض لغرضين مختلفين، واستخدم `git add -p` عشان تعمل Commitين منفصلين.
3. **[صعب]** اكتب Commit فيه عنوان وجسم و Footer فيه `Closes #` رقم Issue حقيقي، من الـ Editor مش بـ `-m`. بعد الـ push، اتأكد إن الـ Issue اتربط.
