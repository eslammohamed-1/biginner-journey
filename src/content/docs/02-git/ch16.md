فيه لحظة هتمر بيها أكيد: عملت reset --hard غلط، أو مسحت Branch فيه شغل يومين، وقلبك وقع في رجليك. الفصل ده هيطمنك: Git فاكر كل مكان HEAD راحله في آخر 90 يوم، في دفتر اسمه reflog. وبعدين أداتين بيخلوك محقق: bisect بيلاقي الـ Commit اللي دخّل الـ Bug بالبحث الثنائي، و blame بيقولك كل سطر اتكتب إمتى ومين وليه.

:::note[بعد الفصل ده هتكون عارف]
- الـ reflog بيسجل إيه، وإزاي تقراه
- ترجّع Commits بعد reset --hard أو Branch اتمسح
- حدود الـ reflog: محلي ومؤقت ومبيحفظش اللي ما اتعملوش Commit
- git bisect خطوة بخطوة، و bisect run الأوتوماتيك
- git blame وأهم الـ Flags بتاعته
- ربط blame بـ log و show عشان تعرف ليه
:::

<a id="s16-1"></a>

## 16.1 الحكاية: "مسحت شغل يومين"

الساعة 1 بالليل، وانت عاوز تنضّف حاجة في التاريخ. قريت على النت إن `git reset --hard HEAD~3` هيحلها. كتبتها، و Enter، وبصيت على `git log`... آخر 3 Commits اختفوا. ومعاهم صفحة الـ Dashboard اللي قعدت فيها يومين. `git log` مش شايفهم. ولا أي Branch بيشاور عليهم.

خد نفس. الـ Commits دي **لسه موجودة**. فاكر إن Git بيخزّن كل Commit كـ Object في `.git/objects`؟ الـ reset مش بيمسح Objects، هو بس حرّك اللافتة لورا. الـ Commits بقت "يتيمة" (مفيش اسم بيشاور عليها)، بس هي هناك. ومحتاجين بس نعرف الـ Hash بتاعها. وهنا ييجي البطل.

<a id="s16-2"></a>

## 16.2 git reflog: دفتر تحركات HEAD

`git log` بيوريك تاريخ **المشروع** (الـ Commits وأبهاتهم). أما `git reflog` (Reference log) فبيوريك تاريخ **انت**: كل مرة HEAD اتحرك فيها على جهازك، بأي سبب: commit، أو switch، أو reset، أو merge، أو rebase، أو amend.

```sh title="Terminal"
$ git reflog
f32164c HEAD@{0}: reset: moving to HEAD~3
2cfdb95 HEAD@{1}: commit: feat: add dashboard charts
8ab01d4 HEAD@{2}: commit: feat: add dashboard layout
5c7e9f2 HEAD@{3}: commit: feat: fetch account data
f32164c HEAD@{4}: checkout: moving from main to feature/dashboard
```

```sh title="قراية الـ reflog"
f32164c
HEAD@{0}
reset: moving to HEAD~3
2cfdb95 HEAD@{1}: commit: ...
```

1. `f32164c`: HEAD كان فين بعد الحركة دي.
2. `HEAD@{0}`: اسم المكان: `{0}` = دلوقتي، `{1}` = الحركة اللي قبلها، وهكذا. وده اسم ينفع تستخدمه في أي أمر زي الـ Hash.
3. `reset: moving to HEAD~3`: إيه اللي حرّكه. هنا الـ reset الغلط.
4. `2cfdb95 HEAD@{1}: commit: ...`: قبل الـ reset على طول، HEAD كان على `2cfdb95`: ده آخر Commit "اختفى". لقيناه.

### الإنقاذ

**تشريح الأمر**

```sh
git reset --hard HEAD@{1}
```

1. `git reset --hard`: حرّك الـ Branch وخلي الورشة زي المكان ده بالظبط (اتأكد إن مفيش تعديلات مش متعملها Commit).
2. `HEAD@{1}`: المكان اللي HEAD كان فيه من حركة واحدة، يعني قبل الـ reset الغلط. وتقدر تكتب الـ Hash `2cfdb95` بدلها.

:::tip[الأأمن: اعمل Branch الأول]
لو مش متأكد إن ده المكان الصح، متعملش reset على طول. اعمل Branch على المكان القديم واتفرج براحتك: `git branch rescue 2cfdb95` ثم `git log --oneline rescue`. لو هو ده، ادمجه أو اعمل reset عليه. الـ Branch مبيضرّش حد.
:::

### إنقاذ Branch اتمسح

مسحت `feature/dashboard` بـ `git branch -D`؟ Git بيطبعلك الـ Hash وهو بيمسح:

```sh title="Terminal"
$ git branch -D feature/dashboard
Deleted branch feature/dashboard (was 2cfdb95).
$ git branch feature/dashboard 2cfdb95      # رجع!
```

ولو الرسالة ضاعت، دوّر في الـ reflog على آخر Commit كنت عليه في الـ Branch ده (`git reflog | grep dashboard`، افتكر `grep` من كتاب الـ Terminal).

**الـ reflog بينقذ إيه؟**

| الموقف | ينفع؟ | الحل |
|---|---|---|
| `reset --hard` غلط | أيوه | `git reset --hard HEAD@{1}` |
| Branch اتمسح بـ `-D` | أيوه | `git branch name <hash>` |
| Rebase بوّظ الدنيا | أيوه | دوّر على `rebase (start)` وارجع للي قبله |
| `commit --amend` وعاوز القديم | أيوه | الـ Commit القديم في `HEAD@{1}` |
| Commits في Detached HEAD | أيوه | `git branch keep <hash>` |
| تعديلات **ما اتعملهاش Commit** واترمت بـ restore أو reset --hard | **لأ** | ملهاش أي أثر في Git |

:::note[لو حابب تتعمق: حدود الـ reflog]
الـ reflog **محلي**: موجود على جهازك بس، ومبيتبعتش لـ GitHub، و `git clone` جديد بيبدأ بـ reflog فاضي. وهو **مؤقت**: Git بيمسح المداخل القديمة أوتوماتيك وقت الصيانة (`git gc`): الافتراضي 90 يوم للمداخل العادية، و 30 يوم للـ Commits اللي بقت مش موجودة في أي Branch (الإعدادين `gc.reflogExpire` و `gc.reflogExpireUnreachable`). وكل Branch ليه reflog خاص بيه كمان: `git reflog show main` أو `main@{2}`، وفيه شكل بالوقت: `main@{yesterday}` و `HEAD@{2.hours.ago}`. وده بالظبط ليه قلنا من أول الكتاب: **اللي اتعمله Commit تقريباً مبيضيعش**.
:::

## 16.3 git bisect: لاقي الـ Commit اللي دخّل الـ Bug

موقف تاني: زرار التحويل في تطبيق البنك كان شغال من أسبوعين في الإصدار `v1.0.0`. النهارده مش شغال. وبينهم 64 Commit. هتفتح كل واحد وتجرّب؟ ده يوم كامل. طب تفتكر لعبة "فكّر في رقم من 1 لـ 100 وأنا أخمّنه"؟ أذكى طريقة إنك تقول 50، والتاني يقولك "أكبر" أو "أصغر"، فتقول 75، وهكذا. كل سؤال بيقسم المسافة نصين. بـ 7 أسئلة بس تلاقي أي رقم من 100. ده اسمه **البحث الثنائي** (Binary search)، و `git bisect` بيعمله على التاريخ: 64 Commit = 6 تجارب بس.

1. <strong>ابدأ:</strong> `git bisect start`.
2. <strong>قوله فين البايظ:</strong> `git bisect bad` (من غير حاجة = HEAD الحالي).
3. <strong>وفين السليم:</strong> `git bisect good v1.0.0` (Tag أو Hash).
4. **Git بيعمل switch** لـ Commit في النص بالظبط (Detached HEAD). جرّب التطبيق.
5. <strong>جاوب:</strong> شغال؟ `git bisect good`. بايظ؟ `git bisect bad`. ومش عارف تختبر الـ Commit ده؟ `git bisect skip`.
6. **كرر** لحد ما Git يقولك `... is the first bad commit` ويعرضه.
7. <strong>ارجع:</strong> `git bisect reset` بيرجّعك للـ Branch اللي كنت عليه.

```sh title="Terminal"
$ git bisect start
$ git bisect bad
$ git bisect good v1.0.0
Bisecting: 31 revisions left to test after this (roughly 5 steps)
[bfef333] feat: add currency formatter
$ git bisect good
Bisecting: 15 revisions left to test after this (roughly 4 steps)
...
4e58f56 is the first bad commit
commit 4e58f565b8178581883a702b51b150635e327e21
    feat: refactor transfer validation
$ git bisect reset
```

**تشريح الأمر**

```sh
git bisect run npm test
```

1. `git bisect run`: بدل ما تجاوب بإيدك، شغّل الأمر ده على كل Commit، وحدد good أو bad من الـ **Exit code** بتاعه.
2. `npm test`: أي أمر: لو خرج بـ `0` يبقى good، ولو من 1 لـ 127 (ما عدا 125) يبقى bad، و `125` = skip. ده نفس الـ Exit codes اللي اتعلمناها في كتاب الـ Terminal، وأي Script بيرجع 0 أو 1 ينفع.

:::note[bisect أوتوماتيك بسطر واحد]
لو الـ Bug إن كلمة معينة ظهرت في ملف، تقدر تختبر بـ grep: `git bisect run sh -c '! grep -q "debugger" app.js'`. الـ `grep -q` بيرجّع 0 لو لقى الكلمة، والـ `!` بتعكس الـ Exit code، فلو الكلمة موجودة = bad. ولما نجرّبها على 8 Commits، Git بيوصل للـ Commit المذنب في تجربتين أو تلاتة.
:::

<a id="s16-4"></a>

## 16.4 git blame: مين كتب السطر ده؟

الاسم بيخوّف ("لوم")، بس الغرض الحقيقي مش إنك تلوم حد، هو إنك تفهم: السطر الغريب ده جه ليه؟ ممكن يكون في سبب منطقي في رسالة الـ Commit اللي ضافه. (ونص المرات هتكتشف إن اللي كاتبه انت من شهرين.)

**تشريح الأمر**

```sh
git blame -L 10,20 app.js
```

1. `git blame`: جنب كل سطر في الملف: آخر Commit غيّره، ومين، وإمتى.
2. `-L 10,20`: Lines: من سطر 10 لـ 20 بس، بدل الملف كله.
3. `app.js`: الملف.

```sh title="Terminal"
$ git blame -L 12,13 app.js
4e58f565 (Sara  2026-10-12 14:02:11 +0300 12)   if (amount > balance) return;
a12c9e40 (Omar  2026-09-30 09:15:40 +0300 13)   balance -= amount;
```

| الأمر | بيعمل إيه |
|---|---|
| `git blame -w file` | تجاهل تغييرات المسافات (عشان Commit الـ Prettier ميطلعش هو "الكاتب" لكل حاجة). |
| `git blame -C file` | اكتشف السطور اللي اتنقلت أو اتنسخت من ملفات تانية. |
| `git show 4e58f565` | الخطوة الجاية: اقرا الـ Commit كله ورسالته عشان تفهم ليه. |
| `git log -L 12,13:app.js` | تاريخ السطرين دول بس عبر كل الـ Commits. |

:::tip[على GitHub و VS Code]
في أي ملف على GitHub فيه زرار **Blame** فوق الكود، وبيخليك تدوس على Commit وترجع لقبله. وفي VS Code إضافة GitLens بتعرض الـ blame جنب السطر وانت واقف عليه. وعشان الـ Formatting commits متلخبطش الـ blame على GitHub، الفرق بتحطها في ملف `.git-blame-ignore-revs`.
:::

:::tip[ملخص الفصل]
- `git reflog` = دفتر كل حركات HEAD على جهازك، و `HEAD@{n}` اسم لأي مكان فيه.
- بينقذ: reset غلط، Branch اتمسح، Rebase بايظ، amend. اعمل `git branch rescue <hash>` الأول.
- مبينقذش اللي ما اتعملهوش Commit، وهو محلي ومؤقت (90/30 يوم).
- `git bisect start / bad / good / reset` بحث ثنائي، و `bisect run` بالـ Exit codes.
- `git blame -L` و `-w`، وبعدين `git show` تعرف ليه.
:::

### صح ولا غلط؟

1. الـ reflog بيتبعت لـ GitHub مع الـ push.
2. `git reset --hard` بيمسح الـ Commits نهائياً من أول لحظة.
3. مع `bisect run`، Exit code صفر معناه Commit سليم.

### أسئلة مراجعة

1. إيه الفرق بين `git log` و `git reflog`؟
2. اكتب خطوات إنقاذ Branch اتمسح بـ `-D`.
3. بين Commit سليم وCommit بايظ فيه 1000 Commit. bisect هيحتاج كام تجربة تقريباً؟ وليه؟
4. ليه `git blame -w` مفيد بعد Commit فيه Format للمشروع كله؟

### تحديات الفصل

<small>جرّبها بإيدك، والحلول في ملحق الإجابات.</small>

1. **[سهل]** اعمل 3 Commits، و `git reset --hard HEAD~3`، ورجّعهم بالـ reflog.
2. **[متوسط]** اعمل Branch فيه Commit، وامسحه بـ `-D`، ورجّعه من غير ما تبص على رسالة المسح (من الـ reflog بس).
3. **[صعب]** اعمل Script بيعمل 20 Commit، ويدخّل كلمة `BUG` في Commit رقم 13. لاقيه بـ `git bisect run` وسطر `grep`.
