مشروعك على GitHub دلوقتي، بس لو حد فتح الصفحة هيلاقي قايمة ملفات وبس. في الفصل ده هنحوّله لحاجة تتفرج عليها: README يشرح المشروع بـ Markdown، وموقع شغال على النت ببلاش بـ GitHub Pages، وروبوت صغير بـ GitHub Actions بيختبر الكود مع كل push، وأداة gh اللي بتعمل كل ده من الـ Terminal.

- README كويس فيه إيه، وأساسيات Markdown بالتفصيل
- نشر مشروع JavaScript عادي على GitHub Pages
- نشر مشروع Vite على Pages بـ Actions و base
- GitHub Actions: الـ Workflow والـ Jobs والـ Steps سطر سطر
- أوامر gh الأساسية: repo و pr و issue و run
:::

## 17.1 الـ README: واجهة مشروعك

تخيل إنك بتقدّم على شغل، والـ Recruiter فتح لينك GitHub بتاعك. عنده 30 ثانية بالكتير لكل مشروع. لو فتح المشروع ولقى قايمة ملفات `index.html` و `script.js` وبس، هيقفل. لو لقى صورة للتطبيق، وجملتين بيقولوا ده بيعمل إيه، ولينك يجرّبه، وقايمة باللي اتعلمته وانت بتعمله، هيقف شوية. الفرق ده كله ملف واحد: `README.md`.

GitHub بيعرض الملف ده أوتوماتيك تحت قايمة الملفات في صفحة أي Repo. والـ `.md` يعني **Markdown**: طريقة تكتب بيها نص منسّق برموز بسيطة، من غير HTML. وانت كـ Content Engineer غالباً قابلتها قبل كده، وهي نفس اللغة اللي بتكتب بيها Issues و PRs والتعليقات على GitHub.

````md title="README.md"
# Bankist
A minimal banking app built with **vanilla JavaScript**.
![App screenshot](docs/screenshot.png)
**Live demo:** [sara.github.io/bankist](https://sara.github.io/bankist/)
## Features
- Login with PIN
- Transfers and loans
- [x] Sorting movements
- [ ] Dark mode
## Run locally
```bash
git clone git@github.com:sara/bankist.git
cd bankist && npx serve .
```
> [!NOTE]
> Demo accounts: js / 1111
| Tech | Why |
|------|-----|
| JS   | course project |
````

1. `# Bankist`: `#` = عنوان كبير (H1). و `##` = H2، لحد `######`. لازم مسافة بعد الـ `#`.
2. `A minimal banking app built with **vanilla JavaScript**.`: `**bold**` = عريض، و `*italic*` = مايل، و `~~text~~` = مشطوب.
3. `![App screenshot](docs/screenshot.png)`: صورة: `!` + النص البديل بين `[ ]` + المسار بين `( )`. حط الصورة جوه الـ Repo.
4. `**Live demo:** [sara.github.io/bankist](https://sara.github.io/bankist/)`: لينك: نفس الصورة من غير `!`.
5. `## Features`: قايمة بـ `-` (أو `*`). و `- [x]` / `- [ ]` = Checkbox (Task list).
6. `## Run locally`: كود: 3 Backticks + اسم اللغة عشان الألوان، وتقفل بـ 3. وكود في نص السطر بـ Backtick واحدة: `` `npm install` ``.
7. `> [!NOTE]`: `>` = اقتباس. و `[!NOTE]` و `[!TIP]` و `[!WARNING]` = صناديق ملونة خاصة بـ GitHub (Alerts).
8. `| Tech | Why |`: جدول: `|` بين الأعمدة، والسطر التاني `---` بيفصل العنوان.

:::tip[README مشروع كورس]
عشان الـ README يبيّن إنك فاهم مش ناسخ: اكتب **اللي اتعلمته** (Closures، الـ Array methods...)، و**اللي ضفته من عندك** زيادة على الكورس، والحاجات اللي ناوي تعملها. ولو المشروع من كورس، اذكر ده بأمانة. واعمل كمان Repo خاص باسم حسابك بالظبط (`sara/sara`): الـ README بتاعه بيظهر في صفحة البروفايل.
:::

## 17.2 GitHub Pages: موقعك على النت ببلاش

مشروع HTML و CSS و JavaScript عادي؟ GitHub Pages بيستضيفه على `https://sara.github.io/bankist/` مجاناً، من غير سيرفر ولا Hosting ولا أي حاجة. ولأنه بيعرض ملفات ثابتة (Static)، فهو مناسب لأي مشروع Frontend، مش لـ Backend بـ Node.

### مشروع Vanilla JS: من غير Build

1. اتأكد إن `index.html` في أول الـ Repo (الجذر)، وإنه اتعمله push على main.
2. على GitHub: **Settings ← Pages**.
3. في **Build and deployment ← Source** اختار **Deploy from a branch**.
4. اختار Branch `main` وفولدر `/ (root)`، و Save.
5. استنى دقيقة أو اتنين، والرابط هيظهر فوق في نفس الصفحة. وكل push جديد على main = الموقع يتحدث لوحده.

:::caution[الموقع شغال بس الـ CSS والصور مش ظاهرين]
غالباً المسارات. موقعك مش على `/`، هو على `/bankist/`. فـ `<link href="/style.css">` (بـ `/` في الأول) هيدوّر على `sara.github.io/style.css` ومش هيلاقيه. استخدم مسارات نسبية: `href="style.css"` أو `./style.css` (افتكر المسارات المطلقة والنسبية من كتاب الـ Terminal). وكمان GitHub Pages بيفرّق بين الحروف الكبيرة والصغيرة: `Logo.png` غير `logo.png`، حتى لو على الـ Mac اشتغلت.
:::

### مشروع Vite: محتاج Build

لو بتستخدم Vite (أو Parcel اللي في كورس Jonas)، الكود اللي بتكتبه مش هو اللي بيتنشر: لازم `npm run build` يطلّع فولدر `dist`. و `dist` في الـ .gitignore. فإزاي GitHub ينشره؟ نخلي GitHub يعمل الـ Build بنفسه بـ Actions. خطوتين:

**1 ·** قول لـ Vite إن الموقع هيبقى في فولدر فرعي:

```js title="vite.config.js"
import { defineConfig } from "vite";

export default defineConfig({
  base: "/bankist/", // اسم الـ Repo بين شرطتين
});
```

**2 ·** في **Settings ← Pages ← Source** اختار **GitHub Actions**، واعمل الملف ده:

```yaml title=".github/workflows/deploy.yml"
name: Deploy to Pages
on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v5
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v5
```

| الأمر | بيعمل إيه |
|---|---|
| `on: push: branches: [main]` | اشتغل مع كل push على main. |
| `permissions` | صلاحيات الـ Token اللي الـ Workflow بيشتغل بيه: يقرا الكود، ويكتب على Pages، و `id-token` عشان يثبت إن النشر جاي من الـ Repo ده. |
| `jobs: build` | هات الكود، وسطّب Node 24، و `npm ci` (تسطيب نضيف من `package-lock.json` بالظبط)، و Build، وارفع `dist` كـ Artifact. |
| `needs: build` | الـ Job التاني (deploy) يستنى الأول يخلص بنجاح. |
| `${{ … }}` | تعبير GitHub Actions: هنا رابط الموقع بعد النشر، بيظهر في صفحة التشغيل. |
| `deploy-pages` | بينشر الـ Artifact على Pages. |

:::note[دقة: الإصدارات دي من أكتوبر 2026]
الأرقام بعد `@` هي الـ Major version للـ Action: `checkout@v7` و `setup-node@v7` (بيشتغلوا على Node 24)، و `upload-pages-artifact@v5` و `deploy-pages@v5`. لو بتقرا الكتاب بعد كده بفترة، شوف صفحة كل Action على GitHub لآخر رقم. وفيه نسخ أقدم في شروحات كتير على النت (`@v3` و `@v4`) لسه ممكن تلاقيها.
:::

## 17.3 GitHub Actions: روبوت بيشتغل مع كل push

شفنا Actions بيعمل Build وينشر. بس استخدامه الأشهر حاجة اسمها **CI** (Continuous Integration): كل push أو PR، GitHub يشغّل الاختبارات والـ Linter على جهاز نضيف في السحابة. لو حاجة فشلت، هتلاقي ✗ حمرا جنب الـ Commit وفي الـ PR، قبل ما الكود البايظ يدخل main. وده بالظبط الـ "Checks" اللي شفناها في صفحة الـ PR ([↩ 11.2](../ch11/#s11-2 "صفحة الـ PR")).

:::note[YAML في سطرين]
**YAML** صيغة لكتابة الإعدادات، شبه JSON بس من غير أقواس: كل سطر `key: value`، والمسافات في أول السطر هي اللي بتقول مين جوه مين (زي Python بالظبط، ومفيش Tab، مسافات بس)، والشرطة `- ` في أول السطر = عنصر في List، و `#` = تعليق. هتشوفها تاني في Docker Compose و Kubernetes، وشرحها الكامل في كتاب APIs و JSON (فصل 21).
:::

الفكرة بسيطة لما تعرف الكلمات: **Workflow** = ملف YAML جوه `.github/workflows/`. جواه **on** = إمتى يشتغل، و **jobs** = شغلانات، كل Job بيشتغل على جهاز (Runner) لوحده، وجوه كل Job **steps** = خطوات ورا بعض: يا `uses` (استخدم Action جاهز) يا `run` (شغّل أمر Shell).

```yaml title=".github/workflows/ci.yml"
name: CI
on:
  push:
    branches: [main]
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test
```

1. `name: CI`: الاسم اللي هيظهر في تاب Actions.
2. `on:`: الـ Triggers: كل push على main، وكل PR.
3. `jobs:`: Job اسمه `test` على جهاز Ubuntu جديد كل مرة.
4. `steps:`: هات كود الـ Repo على الجهاز (من غيرها الجهاز فاضي).
5. `- uses: actions/setup-node@v7`: سطّب Node 24، و `cache: npm` يحفظ المكتبات بين المرات عشان يبقى أسرع.
6. `- run: npm ci`: أوامر Shell عادية. لو أي واحد خرج بـ Exit code غير صفر، الـ Job يفشل والـ ✗ تظهر. نفس فكرة `set -e` من كتاب الـ Terminal.

:::note[ببلاش؟]
للـ Repos الـ Public: Actions مجانية على الـ Runners بتاعة GitHub. للـ Private: فيه دقايق مجانية كل شهر حسب خطتك، وبعدها بفلوس. وتقدر تشوف كل تشغيل وكل سطر Log في تاب **Actions**، وتشغّل Workflow بإيدك لو ضفت `workflow_dispatch:` تحت `on`.
:::

:::caution[الأسرار في Actions]
لو الـ Workflow محتاج API Key، متكتبهوش في الملف أبداً. حطه في **Settings ← Secrets and variables ← Actions**، واستخدمه كده: `${{ secrets.WEATHER_API_KEY }}`. GitHub بيخفيه من الـ Logs.
:::

## 17.4 gh: GitHub من الـ Terminal

كل اللي عملناه في الموقع (Repo جديد، PR، Issues، Releases) ينفع من الـ Terminal بأداة GitHub الرسمية `gh`. تسطيبها على الـ Mac: `brew install gh`، وبعدين `gh auth login` ([↩ 9.5](../ch09/#s9-5 "الطريق 2: HTTPS على الـ Mac بالـ Keychain")).

**تشريح الأمر**

```sh
gh repo create bankist --public --source=. --remote=origin --push
```

1. `gh repo create`: اعمل Repo جديد على GitHub.
2. `bankist`: اسمه.
3. `--public`: عام (أو `--private`).
4. `--source=.`: من الـ Repo المحلي اللي في الفولدر الحالي (الـ `.`) بدل ما يعمل واحد فاضي.
5. `--remote=origin`: ضيفه كـ Remote بالاسم ده (بدل `git remote add`).
6. `--push`: واعمل push للـ Commits على طول. كده الفصل 9 كله في سطر.

**تشريح الأمر**

```sh
gh pr create --fill --base main
```

1. `gh pr create`: افتح PR للـ Branch اللي انت عليه.
2. `--fill`: خد العنوان والوصف من الـ Commits أوتوماتيك.
3. `--base main`: عاوزه يتدمج في main.

**أوامر gh اللي هتستخدمها**

| الأمر | بيعمل إيه |
|---|---|
| `gh repo clone sara/bankist` | clone من غير ما تجيب الرابط |
| `gh repo view --web` | افتح صفحة الـ Repo في المتصفح |
| `gh pr list` / `gh pr status` | الـ PRs المفتوحة / حالة الـ PRs بتاعتك |
| `gh pr checkout 12` | هات Branch الـ PR رقم 12 عندك عشان تجرّبه |
| `gh pr diff 12` | اعرض الـ diff بتاعه |
| `gh pr merge 12 --squash --delete-branch` | ادمجه Squash وامسح الـ Branch |
| `gh issue create -t "title" -b "body"` | Issue جديد (`-t` عنوان و `-b` Body) |
| `gh issue list --label bug` | الـ Issues بـ Label معين |
| `gh run list` / `gh run watch` | تشغيلات Actions / تابع اللي شغال لايف |
| `gh release create v1.0.0 --generate-notes` | Release ([↩ 14.5](../ch14/#s14-5 "الـ Releases على GitHub")) |

:::tip[حاجة مشتركة: نفس شكل git]
`gh` ماشي على نفس النمط: برنامج + موضوع (`repo` و `pr` و `issue`) + فعل (`create` و `list` و `view`) + Flags. و `gh help` و `gh pr create --help` للمساعدة، و `--web` في أوامر كتير بتفتح نفس الحاجة في المتصفح.
:::

:::tip[ملخص الفصل]
- README بـ Markdown: `#` عناوين، `**` عريض، `[]()` لينك، `![]()` صورة، و 3 Backticks للكود.
- Pages لمشروع عادي: Deploy from a branch، ومسارات نسبية.
- Vite: `base: "/repo/"` + Workflow بيعمل Build وينشر `dist`.
- Actions: `on` و `jobs` و `steps` (`uses` أو `run`)، وأي Exit code غير صفر = فشل.
- `gh`: `repo create --source=. --push` و `pr create --fill` و `pr checkout`.
:::

### صح ولا غلط؟

1. GitHub Pages ينفع يشغّل Backend بـ Express.
2. في مشروع على Pages، `href="/style.css"` هيشتغل عادي.
3. كل Job في Actions بيشتغل على جهاز جديد.

### أسئلة مراجعة

1. اكتب README صغير فيه عنوان، وصورة، ولينك، وقايمة، وبلوك كود.
2. ليه مشروع Vite محتاج `base` على Pages؟
3. اشرح الفرق بين `uses` و `run` في الـ steps.
4. إزاي تحط API Key يستخدمه الـ Workflow من غير ما يتكتب في الكود؟

### تحديات الفصل

<small>جرّبها بإيدك، والحلول في ملحق الإجابات.</small>

1. **[سهل]** انشر مشروع HTML بسيط من الكورس على GitHub Pages بـ Deploy from a branch.
2. **[متوسط]** اكتب README للمشروع فيه Screenshot ولينك الـ Live demo و Features كـ Task list.
3. **[صعب]** ضيف Workflow CI بيعمل `npm ci` و `npm test`، واعمل PR فيه اختبار فاشل عمداً عشان تشوف الـ ✗، وبعدين صلّحه.
