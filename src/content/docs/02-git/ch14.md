<small>المرحلة 5 · الشغل المنظّم</small>

أداتين صغيرين بيحلوا مشاكل كبيرة. الـ Stash: انت في نص شغل ومش جاهز تعمل Commit، وفجأة لازم تروح Branch تاني تصلّح حاجة. خبّي شغلك على جنب وارجعله. والـ Tags: علامة ثابتة على Commit مهم زي v1.0.0، ومنها بتعمل Release على GitHub فيه وصف وملفات للتحميل.

:::note[بعد الفصل ده هتكون عارف]
- المشكلة اللي git stash بيحلها
- stash push و list و show و pop و apply و drop
- stash للملفات الجديدة بـ -u، و stash لـ Branch جديد
- يعني إيه Tag والفرق بين Lightweight و Annotated
- Semantic Versioning: Major و Minor و Patch
- push للـ Tags وعمل Release على GitHub
:::

<a id="s14-1"></a>

## 14.1 المشكلة: لازم أسيب اللي في إيدي دلوقتي

الساعة 4 العصر، وانت في نص الـ Dropdown الجديد في الـ Navbar على `feature/navbar`. نص الكود مكتوب، والقايمة بتفتح بس مش بتقفل، وفيه `console.log` في 6 أماكن. فجأة رسالة: "الـ Contact form على الموقع مش بتبعت حاجة، والعميل هيفتح الموقع كمان ساعة!".

لازم تروح main وتعمل Branch للإصلاح دلوقتي. بس تعمل إيه في الشغل اللي في إيدك؟ لو عملت `git switch main`، يا Git يرفض عشان تعديلاتك هتتمسح ([↩ 7.5](../ch07/#s7-5 "git switch: اتنقّل بين الـ Branches"))، يا يسمح وينقل تعديلات الـ Navbar معاك لـ main فتتخلط مع الإصلاح. تعمل Commit؟ لكود بايظ مليان `console.log`؟ تنسخ الملفات في فولدر على الـ Desktop؟ رجعنا لأيام `final-final2`. محتاج حاجة زي الدرج اللي في المكتب: تشيل الورق اللي على المكتب كله وتحطه فيه، تشتغل على الموضوع المستعجل على مكتب نضيف، وبعدين تطلّع الورق تاني بنفس ترتيبه.

<strong>الحل: `git stash`</strong> = خد كل التعديلات اللي مش متعملها Commit، وحطها في درج على جنب، ورجّع الورشة `clean`.

![الـ Stash درج (Stack): آخر حاجة تتحط فيه هي stash@{0} .](./assets/ch14-fig1.png)

*الـ Stash درج (Stack): آخر حاجة تتحط فيه هي stash@{0}.*

## 14.2 أوامر الـ Stash

**تشريح الأمر**

```sh
git stash push -u -m "wip: navbar dropdown"
```

1. `git stash push`: خبّي التعديلات (`git stash` لوحدها = `git stash push`).
2. `-u`: Include Untracked: خبّي الملفات الجديدة كمان. من غيرها الملفات الجديدة **بتفضل** في الورشة (ومش هتبقى clean).
3. `-m "wip: navbar dropdown"`: اسم للـ Stash ده عشان تفتكره، بدل الاسم الأوتوماتيك "WIP on main: 9f1c2ab...".

```sh title="Terminal"
$ git stash push -u -m "wip: navbar dropdown"
Saved working directory and index state On feature/navbar: wip: navbar dropdown
$ git status
nothing to commit, working tree clean
$ git stash list
stash@{0}: On feature/navbar: wip: navbar dropdown
stash@{1}: On main: try new colors
```

**أوامر git stash**

| الأمر | بيعمل إيه |
|---|---|
| `git stash list` | اعرض الدرج كله. `stash@{0}` الأحدث |
| `git stash show -p stash@{1}` | اعرض الـ diff بتاع Stash معين (`-p` = Patch كامل، من غيرها ملخص) |
| `git stash pop` | رجّع آخر Stash للورشة **وامسحه** من الدرج |
| `git stash apply stash@{1}` | رجّعه بس **سيبه** في الدرج (لو عاوز تطبقه على أكتر من Branch) |
| `git stash drop stash@{1}` | امسح Stash معين |
| `git stash clear` | امسح الدرج كله (من غير رجوع تقريباً) |
| `git stash branch try/x stash@{0}` | اعمل Branch جديد من المكان اللي اتعمل فيه الـ Stash وطبّقه عليه |
| `git stash -p` | خبّي حتت معينة بس (زي `add -p`) |

:::tip[حاجة مشتركة: {n}@ والـ Stack]
الـ `stash@{0}` هو نفس شكل `HEAD@{1}` اللي هتشوفه في الـ reflog (الفصل 16): اسم + `@{رقم}`. وفي zsh أو PowerShell لو الأقواس عملت مشكلة حطها بين Quotes: `"stash@{1}"` (نفس فكرة `HEAD^` في الفصل 4).
:::

### السيناريو كامل

```sh title="Terminal"
git stash push -u -m "wip: navbar"    # خبّي
git switch main && git pull
git switch -c fix/contact-form
# ... صلّح، Commit، push، PR ...
git switch feature/navbar
git stash pop                          # رجّع شغلك وكمّل
```

:::danger[مشكلة: stash pop عمل Conflict]
الـ `pop` طلع `CONFLICT` لأن الملف اتغير من ساعة ما عملت stash.

<strong>الحل:</strong> حل الـ Conflict عادي زي الفصل 8 (العلامات و `git add`). المهم: لما الـ pop يعمل Conflict، الـ Stash **مش بيتمسح** من الدرج (عشان أمان). بعد ما تحل وتتأكد، امسحه بإيدك: `git stash drop`.
:::

:::note[لو حابب تتعمق: الـ Stash من جوه]
الـ Stash مش سحر: هو Commits عادية بس مستخبية. كل Stash = Commit ليه 2 أو 3 Parents: آخر Commit كنت عليه، و Commit فيه حالة الـ Staging، ولو استخدمت `-u` Commit تالت فيه الملفات الجديدة. جرّب `git cat-file -p stash@{0}` هتلاقي سطور `parent` كتير. والدرج نفسه Ref اسمه `refs/stash`، و `stash@{1}` مجرد الـ reflog بتاعه (عشان كده نفس شكل `HEAD@{1}`). ودي فايدة عملية: لو عملت `drop` بالغلط، Git طبعلك `Dropped refs/stash@{0} (36ff05b...)`، فـ `git stash apply 36ff05b` بيرجّعه، لأن الـ Commit لسه موجود لحد ما Git ينضّف.
:::

:::caution[الـ Stash مش مكان تخزين]
الـ Stash محلي (مبيتبعتش على GitHub)، وسهل تنساه، والدرج بيتملي حاجات مش فاكر هي إيه. استخدمه للمواقف السريعة (دقايق أو ساعات). أي حاجة هتعيش أكتر من كده: Commit على Branch (حتى لو اسمه `wip:`) واعمله push.
:::

## 14.3 الـ Tags: علامة ثابتة على Commit

بعتّ لينك البورتفوليو لشركة في أول الشهر، وبعدها كمّلت شغل: غيّرت التصميم، وضفت صفحة، وشلت مشروع قديم. بعد أسبوعين الشركة كلمتك: "عجبنا المشروع اللي كان في الصفحة التانية، ممكن تبعتلنا نفس النسخة؟". النسخة دي فين؟ هتعمل `git log` وتدوّر على Commit من "أول الشهر تقريباً"؟ كان المفروض يوم ما بعتّ اللينك تحط علامة: "النسخة دي اللي اتبعتت".

العلامة دي اسمها **Tag**. الـ Branch لافتة **بتتحرك** مع كل Commit. الـ **Tag** لافتة **ثابتة**: بتتحط على Commit مهم وتفضل عليه للأبد. أشهر استخدام: أرقام الإصدارات (`v1.0.0`).

**نوعين Tags**

| النوع | الأمر | فيه إيه |
|---|---|---|
| Lightweight | `git tag v1.0.0` | مجرد اسم على Commit |
| **Annotated** | `git tag -a v1.0.0 -m "msg"` | Object كامل: مين عمله، وإمتى، ورسالة. **استخدمه للإصدارات** |

**تشريح الأمر**

```sh
git tag -a v1.0.0 -m "First public release" 9f1c2ab
```

1. `git tag`: إدارة الـ Tags. من غير Arguments = اعرضهم.
2. `-a`: Annotated.
3. `v1.0.0`: الاسم. الـ `v` في الأول متعارف عليه.
4. `-m "First public release"`: رسالة الـ Tag.
5. `9f1c2ab`: اختياري: الـ Commit. من غيره = HEAD.

| الأمر | بيعمل إيه |
|---|---|
| `git tag` | اعرض كل الـ Tags. و `git tag -l "v1.*"` بـ Pattern. |
| `git show v1.0.0` | تفاصيل الـ Tag والـ Commit اللي عليه. |
| `git push origin v1.0.0` | ابعت Tag واحد. (push العادي مش بيبعت Tags). |
| `git push --follow-tags` | ابعت الـ Commits ومعاها الـ Annotated tags اللي عليهم. |
| `git tag -d v1.0.0` | امسح محلياً. ومن GitHub: `git push origin --delete v1.0.0`. |
| `git switch --detach v1.0.0` | اتفرج على المشروع زي ما كان في الإصدار ده (Detached HEAD). |

## 14.4 Semantic Versioning: معنى الأرقام

ليه `v1.0.0` ومش `v1` أو `v2026-10`؟ تخيل إنك بتستخدم مكتبة، وطلع منها إصدار جديد. السؤال الوحيد اللي يهمك: "لو حدّثت، الكود بتاعي هيتكسر؟". لو الأرقام عشوائية، لازم تقرا كل التغييرات عشان تعرف. نظام **Semantic Versioning** (SemVer) بيحط الإجابة في الرقم نفسه: كل جزء من التلاتة ليه معنى ثابت، فمجرد ما تشوف الرقم اتغير إزاي، تعرف المخاطرة.

![SemVer: MAJOR.MINOR.PATCH ، ومرتبطة بأنواع Conventional Commits.](./assets/ch14-fig2.png)

*SemVer: MAJOR.MINOR.PATCH، ومرتبطة بأنواع Conventional Commits.*

ودي نفس الأرقام اللي بتشوفها في `package.json` بتاع أي مكتبة npm (`"vite": "^7.1.2"`). الـ `^` هناك معناها "أي Minor أو Patch أحدث، بس نفس الـ Major" لأن الـ Major بيكسر.

## 14.5 الـ Releases على GitHub

الـ Tag معلومة جوه Git: مبرمج يفهمها، بس صاحبك اللي عاوز يجرّب برنامجك مش هيعمل `git switch --detach v1.0.0`. محتاج صفحة يقرا فيها "إيه الجديد" ويدوس Download. وده اللي GitHub بيضيفه فوق الـ Tag.

الـ **Release** = Tag + صفحة على GitHub فيها عنوان، و Release notes (إيه الجديد)، وملفات للتحميل (GitHub بيحط Zip للكود تلقائياً).

1. اعمل Tag وابعته: `git tag -a v1.0.0 -m "v1.0.0"` و `git push origin v1.0.0`.
2. على GitHub: **Releases ← Draft a new release**، اختار الـ Tag.
3. دوس **Generate release notes**: GitHub يجمع عناوين الـ PRs اللي اتدمجت من آخر Release.
4. عدّل، ضيف ملفات لو فيه (مثلاً Build مضغوط)، و **Publish release**.

**تشريح الأمر**

```sh
gh release create v1.0.0 --generate-notes
```

1. `gh release create`: اعمل Release من الـ Terminal (الفصل 17).
2. `v1.0.0`: الـ Tag. لو مش موجود على GitHub، `gh` بيعمله على آخر Commit في الـ Branch الافتراضي.
3. `--generate-notes`: اكتب الـ Release notes أوتوماتيك من الـ PRs.

:::tip[لمشاريعك الشخصية]
حتى في مشروع الـ Portfolio، Tag زي `v1.0.0` لما تنشر أول نسخة بيديك نقطة ترجعلها بسهولة: "النسخة اللي بعتها للشركة الفلانية". والـ Releases بتخلي صفحة المشروع على GitHub شكلها محترف.
:::

:::tip[ملخص الفصل]
- `git stash push -u -m "..."` يخبّي كل حاجة حتى الجديد، و `pop` يرجّع ويمسح، و `apply` يرجّع ويسيب.
- `stash list` و `show -p` و `drop`، والـ Conflict في pop مبيمسحش الـ Stash.
- الـ Tag لافتة ثابتة، و `-a` Annotated للإصدارات، والـ push بيتعمل له لوحده.
- SemVer: MAJOR بيكسر، MINOR ميزة، PATCH إصلاح.
- Release = Tag + صفحة و Notes، من الموقع أو `gh release create`.
:::

### صح ولا غلط؟

1. `git stash` من غير `-u` بيخبّي الملفات الجديدة Untracked.
2. `git push` العادي بيبعت الـ Tags.
3. لو مكتبة طلعت من 2.4.1 لـ 3.0.0 يبقى غالباً فيه تغيير بيكسر.

### أسئلة مراجعة

1. إيه الفرق بين `stash pop` و `stash apply`؟
2. إمتى الـ Stash ميكونش الحل الصح؟
3. إيه الفرق بين Tag و Branch؟ وبين Lightweight و Annotated؟
4. مشروعك على 1.3.2: إيه الرقم الجاي لو ضفت ميزة؟ ولو صلحت Bug؟ ولو غيرت شكل API بيكسر؟

### تحديات الفصل

<small>جرّبها بإيدك، والحلول في ملحق الإجابات.</small>

1. **[سهل]** عدّل ملفين، اعمل `git stash push -m "test"`، اتأكد إن الورشة clean، وبعدين `git stash pop`.
2. **[متوسط]** اعمل ملف جديد وعدّل ملف قديم، وجرّب `git stash` من غير `-u`: إيه اللي اتخبّى وإيه اللي فضل؟ وبعدين بـ `-u`.
3. **[صعب]** اعمل Tag `v0.1.0` Annotated على الـ playground وابعته، واعمل Release من الموقع بـ Generate release notes.
